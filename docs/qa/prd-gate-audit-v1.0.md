## 审计一：AC 可执行性与验收方式覆盖

主要发现（15 项 AC 可执行性问题 + 11 项覆盖不足），已全部修订：

- 大量 AC 含主观词（"可见的等待指示""明确的引导信息""与 TUI 对等""diff 有意义"）且无客观判据
- M4/M5 多个条目的 AC 未按编号拆分，无法定位到具体测试用例
- **PRD-M6-004 用"真人验收"，直接违反本文档 §0.2 自己定的规则**（没有可执行验收方式的条目不允许存在）
- **PRD-M6-001 的 AC "API 从 ≥5 个内置能力抽象而来"描述的是设计过程而非可观测行为**，无法测试
- 多个条目的 AC 跨层（后端逻辑 + TUI 渲染），但验收方式只给了后端测试文件
- PRD-M1-004 把"缓存命中率 ≥80%"作为硬性 pass/fail，但它依赖 provider 非确定性行为

## 审计二：一致性、不变量、遗漏、优先级

**内部矛盾**
- PRD-M1-005 结构化输出的用户价值写的是"给摘要/记忆抽取用"，但 M1 明确不做这两个
- 多个 P0 条目的真实验收在 nightly（不进 CI 门禁），"P0 完成"无法被客观判定
- M2-004 跨会话检索 与 M1"不做会话搜索"边界不清

**不变量守护缺口**
- **INV-01 最严重**：唯一挂靠条目只验证 append-only 与崩溃重放，**没有任何 AC 测试"schema 演进后旧事件仍可解析"**
- INV-04：M3 拆 daemon 时未要求审计 M0–M2 期间 TUI 里已积累的业务逻辑，存在隐性返工
- INV-08 只在验收方式文本里零散提及，从未成为可核查项
- INV-07 / INV-10 零引用 —— 判定为**非缺口**，二者是流程约束不是产品需求

**遗漏（8 项，已全部补充或显式声明范围）**
并发写仲裁 · 事件 schema 迁移 · 卸载与数据清理 · 日志与故障排查 · 长任务完成通知 · provider 故障降级 · 时区展示 · 无障碍

**优先级**
40 条中 34 条 P0（85%），分级形同虚设。已逐个里程碑对照 DoD 重排。

## 修订结论

PRD v1.0 → v1.1：条目 40 → 45，P0 占比 85% → 71%（M0/M6 本就是最小集合，全 P0 合理），
