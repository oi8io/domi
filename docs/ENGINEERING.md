# domi — 工程推进规约

> 怎么推进，而不是推进什么。配合 DESIGN.md 使用。
> v0.1 · 2026-08-24

---

## 0. 这份文档要解决的问题

DESIGN.md 回答了"做什么"，但一个人在业余时间做一个 4–10 个月的项目，**死法从来不是想不清楚做什么，而是**：

- 第 3 个月发现架构腐化了，重构成本大到只能弃坑
- 写了三个月没有测试，之后不敢动任何东西
- 每次隔一周再开工，前 40 分钟都在回忆"我上次在干嘛"
- 做了一堆基础设施，但从来没有一个能跑通的东西

这份文档就是针对这四种死法的工程对策。

---

## 1. 切片方式：Walking Skeleton，不是自底向上

**最常见的错误做法**：先把 `kernel` 写完美 → 再写 `store` → 再写 `model` → 最后写 TUI。三个月后你有四个精美的包和零个能跑的东西，而且它们拼不到一起。

**正确做法**：第一周就打通一条**最细的端到端线**，每个环节都用最丑陋的实现：

```
键盘输入 → user.input 事件 → 写 SQLite → buildContext(最朴素:全量拼)
  → 调一个硬编码的 Anthropic → 流式 delta 事件 → 一个写死的 fs.read tool
  → tool.result 事件 → TUI 渲染
```

这条线里：`buildContext` 可以是 `events.map(toMessage)`，权限可以是 `return true`，TUI 可以只有一个滚动区。**但它必须真的跑通。**

理由有三个：
1. 集成风险是所有风险里最贵的，越晚暴露越贵
2. 有了这条线，之后每个功能都是"替换其中一环"，而不是"新建一个模块然后祈祷能接上"
3. 心理上，一个能跑的丑东西比四个完美的半成品有用一百倍

**推论：任何时刻 main 分支都必须能跑。** 不接受"这个包写完了但还没接上"的状态。

## 2. 测试策略：agent 项目的生死线

这是 agent 项目最难、也最容易被跳过的部分。典型剧本是：LLM 输出不确定 → 没法断言 → 干脆不写测试 → 三个月后改压缩策略时不敢动 → 弃坑。

**事件流架构给了你一个别人没有的解法：把"决策"和"效果"分离。kernel 的输出是事件，事件是纯数据，纯数据可断言。**

### 三层测试金字塔

**第一层 · 纯函数单测（占 70%，毫秒级，完全确定）**

这些东西根本不需要 LLM：

- `buildContext(events, policy) → messages` —— 给定事件流，断言拼出的上下文
- `compactor.compact(events) → summary` 的**触发逻辑与切分边界**（不测摘要文本质量）
- 提示词分层的拼装顺序与 cacheable 边界
- 权限引擎：给定 spec 和请求，断言 allow/ask/deny
- 事件流的分支、重放、seq 一致性

这一层能覆盖 domi 大部分真正复杂的逻辑。**如果你发现某个逻辑没法这样测，说明它和 IO 耦合了，应该重构。测试难写本身就是架构信号。**

**第二层 · 录制回放（占 25%，秒级，确定）**

VCR / cassette 模式，这是让 agent 项目可测的关键技巧：

```
DOMI_RECORD=1 bun test    # 跑真实模型，把响应流录进 fixtures/
bun test                  # CI 默认：ReplayProvider 从 fixture 读，零网络零成本
```

实现上就是 `ModelProvider` 接口多一个 `ReplayProvider` 实现。**关键细节：fixture 存的是模型的原始 SSE 响应流，不是最终结果。** 这样 tool 执行、权限检查、事件生成、压缩触发全都还在真实跑，只有"模型推理"这一步被固定住了。

这一层测的是完整循环：多轮工具调用、错误恢复、压缩触发、子任务派生。

**第三层 · 真实 eval（占 5%，分钟级，非确定）**

10–20 个真实任务场景，跑真实模型，人工或用 LLM 打分。

**这一层绝对不能进 CI 门禁**——模型抖动会让它随机变红，几次之后你就会开始无视 CI，那时整套测试体系就废了。放 nightly，结果写进一个趋势文件，人工看。

### 一条硬规则

**修 bug 的流程固定为：先写一个能复现的失败测试 → 再修。** 对 agent 项目尤其重要，因为很多 bug 是"某种事件序列下的状态错乱"，不落成 fixture 就会反复回归。

## 3. 架构守卫：三道自动化防线

架构不会被一次大重构毁掉，它是被一百次"就这一次，先这样"腐蚀掉的。靠自觉守不住，必须自动化。

**第一道 · 依赖边界（CI 阻断）**

`dependency-cruiser` 规则，第一天就配：

- `kernel` → 不得依赖 `apps/*`、不得依赖 `store`/`mcp` 的实现（只能依赖接口包）
- `client-core` → 不得依赖任何 Node 专属 API（保证浏览器能跑）
- 任何包 → 不得循环依赖

**第二道 · 物理隔离（比规则更硬）**

`packages/kernel/package.json` 的 `dependencies` 保持接近空。物理上装不了 `fs`、装不了 SDK，就写不出违规代码。这比任何 lint 规则都可靠。

**第三道 · API 快照**

`packages/protocol` 的公开类型做快照测试（`api-extractor` 或简单地把类型 dump 成 `.api.md` 提交进仓库）。任何协议变更会在 diff 里显式出现，**逼你在 commit 时意识到"我正在改契约"**。这一条能挡掉大量无意识的破坏性变更。

## 4. 契约演进：先行，但不要过度设计

"契约先行"最容易走偏成"第一周设计一个完美的协议"。正确的度是：

**用 zod 定义，一处定义三处受益**——运行时校验、类型推导、生成 JSON Schema 给非 TS 客户端。

**只定义当前里程碑需要的事件。** M0 只需要 6 个事件类型，就只定义 6 个。事件流是 discriminated union，**新增成员天然向后兼容**，这是这个数据结构最大的红利。

**但演进纪律必须第一天就立**：

- 事件类型**只增不改**。字段可加不可删、不可改语义。
- 需要改语义时，新增一个事件类型，老的标 `@deprecated` 但保留解析能力。**事件流是 append-only 的，历史数据永远存在，你永远得能读懂三个月前的事件。**
- daemon ↔ client 握手时协商 protocol version，**不匹配就明确报错**，绝不"尽力兼容"——诡异行为比明确失败难调试十倍。

**冻结时间点**：M0–M1 期间 protocol 可以随便改（此时只有你自己在用）。**M3 三端并存之后冻结**，之后只走增量演进。把这个日期写进 ADR。

## 5. 节奏管理：对抗上下文丢失

单人业余项目的头号杀手不是技术难度，是**"隔了 5 天再打开编辑器，前 40 分钟在回忆自己在干嘛"**。这个损耗累积起来能吃掉 30% 的有效时间。

三个极简机制，总维护成本每次 3 分钟：

**`NEXT.md`（仓库根目录，三行）**

```
在做: M1 · ModelProvider 的 Gemini 实现
下一步: 补 tool call 的 schema 转换（Gemini 的 function declaration 格式不同）
卡在: Gemini 的流式 thinking 字段格式没查清楚，见 TODO(gemini-think)
```

**每次收工前更新它**，这是纪律。下次开工先读它，40 分钟压缩到 2 分钟。

**`docs/adr/` 极简架构决策记录**

一个决策一个文件，10 行以内，只写三段：

```md
# 007 事件类型只增不改
Context: 事件流 append-only，历史数据必须永远可解析
Decision: 事件类型只新增；字段可加不可删；改语义就新增类型 + @deprecated 旧的
Consequences: 类型定义会逐渐膨胀；换来任意历史会话永远可读、可重放
```

ADR 的价值不在于给别人看，在于**三个月后的你不会推翻自己想清楚过的事**。DESIGN.md 里那三个不可逆决策，第一天就各写一条 ADR。

**任务粒度 ≤ 半天，且必须以"可运行"结尾**

不接受跨天的半成品状态。做不完就砍范围，不要留断裂的 main。不要开长命分支——单人项目的分支只会变成上下文债。

## 6. Dogfooding：最强的质量飞轮，但有陷阱

**时间点：M1 结束后强制自用。** 不要更早（太难用会挫伤自己），不要更晚（越晚积累的错误设计越多）。

**渐进式接管，每一级过关了再进下一级**：

1. domi 生成自己的 commit message
2. domi 写自己的单元测试
3. domi 处理自己的 issue
4. domi 实现自己的 feature

**"用不下去的地方"是比任何用户调研都准的信号，直接进 P0。**

**但要防 dogfooding 陷阱**：为了自己爽而做偏门功能，做出一个只有你能用的东西。用一条规则约束——**只有当"我第三次因为同一件事卡住"，才把它变成 feature**。前两次手动绕过去。

---

## 7. 风险前置：按"错了代价多大"排序

不按"难度"排，按"发现得晚会多疼"排：

| 风险 | 验证时机 | 验证方式 | 错了怎么办 |
|---|---|---|---|
| Bun + OpenTUI 是否可靠 | **M0 第 1–2 天** | 2 天 spike：高频流式输出下的渲染性能、native 模块兼容 | 退回 Node 22 + Ink，架构不受影响 |
| 长会话下 `buildContext` 性能 | **M0 内** | 合成 5 万条事件的会话，压测拼装耗时 | 加物化视图 / 增量拼装。**M0 发现 = 改一个函数；M4 发现 = 改整个 store 层** |
| prompt cache 是否真命中 | **M1 内** | 实测缓存命中率，不看文档看账单 | 重排提示词分层。没打对成本差 5–10 倍 |
| 跨端状态同步延迟 | M3 | 三端同时开，观察事件推送延迟 | 加本地乐观更新 |

**spike 代码必须删掉重写。** 不允许"跑通了就顺手留下"——spike 是为了回答问题，不是为了产出代码。这条不守，你的地基里会永远埋着两天赶出来的东西。

## 8. CI 该跑什么，不该跑什么

**每次 push 跑**（目标 < 3 分钟，超过就会开始有人跳过）：
typecheck · lint · 依赖边界 · 单测 · replay 测试 · 三端构建产物

**绝不跑**：真实 LLM 调用。慢、贵、flaky。一个会随机变红的 CI 等于没有 CI。

**nightly 跑**：真实 eval 套件 · MCP server 兼容性测试 · 依赖安全扫描

**Release 前人工过**：eval 分数趋势 · 三端手动冒烟 · 单二进制在干净机器上能起来

## 9. 发布工程

**版本管理**：changesets。monorepo 多包发版靠手工必然出错。

**三种分发渠道，覆盖不同人群**：

1. `npx domi` / `bunx domi` —— 开发者尝鲜，零安装门槛
2. **单二进制**（`bun build --compile`）—— 这条对 TUI 工具的采用率影响被严重低估。很多潜在用户不想为了试一个工具装 Node
3. Homebrew / Scoop（M4 后）—— 长期用户

**版本号**：v1.0 之前用 0.x，明确告诉用户会有破坏性变更，给自己留改的余地。别为了显得成熟提前上 1.0，那会把自己焊死。

## 10. 仓库与社区的工程节奏

**M0 就 public，但不宣传。** 三个理由：commit history 本身是叙事资产（"从第一天就在做"很有说服力）；public 会潜移默化逼你保持整洁；早期没人看，试错成本为零。

分阶段开放：

- **M0**：public repo，README 只写一句话定位 + "早期开发中，暂不接受 PR"
- **M1**：开 Discussions（比 Issues 门槛低，适合收早期反馈）
- **M2**：开 Issues + 模板，挂 5 个 `good first issue`
- **M4**：CONTRIBUTING.md + 文档站

**最适合外部贡献的两个点**（因为自包含、易 review、不碰核心）：新增一个 `ModelProvider`、新增一个 Skill。给这两个各写一份"照着做"的模板和 checklist，能显著提高贡献转化率。

**别过早接受核心重构类 PR。** 单人项目在架构稳定前，一个善意的大 PR 可能比帮助更麻烦——你既不好拒绝，合了又会失去对代码的掌控感。

---

## 11. 一句话总结每条

1. 第一周打通一条最丑的端到端线，之后所有工作都是替换其中一环
2. 纯函数单测 70% + 录制回放 25% + 真实 eval 5%，eval 绝不进 CI 门禁
3. 依赖边界 / 物理隔离 / API 快照，三道自动化防线代替自觉
4. 契约用 zod、只定义当前需要的、事件只增不改、M3 后冻结
5. `NEXT.md` 三行 + 极简 ADR，对抗业余项目的上下文丢失
6. M1 后强制 dogfood，但"第三次卡住"才准变成 feature
7. 按"发现得晚会多疼"排序做 spike，spike 代码必须删
8. CI 3 分钟内跑完且永不 flaky，真实模型调用只进 nightly
9. 单二进制分发的重要性被严重低估
10. M0 就 public 但不宣传，M4 前不接核心重构 PR
