# domi — 研发流程规约

> 回答一个问题：怎么保证三个月后这个项目还没被腐蚀。
> v0.1 · 2026-08-24 · 配合 DESIGN.md / ENGINEERING.md 使用

---

## 0. 对"四角色流程"的评估

提出的流程是：**产品专家出 PRD → 资深架构师出 SPEC → 资深工程师 TDD 实现 → 骨灰级测试工程师按 PRD 验收。**

**骨架是对的，而且对了三件关键的事**：

1. **强制切换关注点**。单一视角写代码，会不自觉地把"需求"改成"我好实现的样子"。这在 AI 执行时尤其严重——同一个模型在同一段上下文里，写 PRD 和写实现的思维是连着的，会自动向"容易写的实现"塌缩。分角色是目前唯一有效的对抗手段。
2. **闭环回到起点**。第 4 步用第 1 步验收，这条闭环是防跑偏的骨架。很多流程死在只有 1→2→3 没有 →1。
3. **可跟踪可中断可继续**。这一条抓得准——业余项目的最大损耗不是技术难度，是上下文丢失。

**但它不够。缺五样东西，每一样都是腐蚀入口。**

---

## 1. 五个缺口与补丁

### 缺口一：这是瀑布，而 domi 是探索性项目

四个角色串行走一遍 = 一次瀑布。而 domi 里有大量"试了才知道"的东西（OpenTUI 行不行、压缩策略哪个好、soul 该沉淀什么）。一次性写完 6 个里程碑的完整 PRD，**必然在 M2 就作废**，然后你会面临"改 PRD 太麻烦，先按代码来吧"——腐蚀从这一刻开始。

**补丁：四个角色不是项目的四个阶段，是每个里程碑内部的四个环节。**

```
M0: PM → 架构 → 工程 → QA → 复盘
M1: PM → 架构 → 工程 → QA → 复盘
...
```

PRD 分册：`docs/prd/M0.md`、`M1.md`……全局只有一份 3 页的 `PRD-VISION.md` 定不变量。

**每册 PRD 在上一个里程碑的 QA 结束后才写**，这样它能吸收上一轮学到的东西。

### 缺口二：没有回写门（最重要的一条）

原流程是单向的。但现实一定会发生：

- 工程师实现到一半发现 PRD 里两条需求互相矛盾
- 测试工程师发现 PRD 某条根本没法验收

**如果没有强制回写机制，下游会"就地修正"——我知道 PRD 写错了，我按对的写。** 这看起来是负责任，实际上是腐蚀的头号来源：一个月后 PRD 和代码各说各话，PRD 变成废纸，此时你已经没有任何防跑偏的基准了。

**补丁：回写门（Write-Back Gate）。硬规则——**

> 任何下游角色发现上游文档有问题，**必须停下，回到上游角色修改文档，再重新往下走**。
> 严禁"心里知道文档错了，代码按正确的写"。
> 回写要留痕：文档改动单独一个 commit，message 前缀 `docs(writeback):`，说明是哪个下游环节触发的。

回写不是流程失败，**回写次数是流程健康度指标**。M0 回写 5 次很正常；如果某个里程碑零回写，大概率是下游在偷偷绕过，而不是上游写得完美。

### 缺口三："跑偏"没有定义，于是无法判定

"不会跑偏的 PRD" 这个要求内部是矛盾的：PRD 越完整越容易在探索性项目里写出无法落地的东西；越可落地就越要留白。

**根本问题是"跑偏"没被定义。** 如果跑偏 = "和 PRD 任何一处不一致"，那你每周都在跑偏，判定就失效了。

**补丁：PRD 分两层。**

```
不变量 Invariants     —— 任何情况下不得违反。违反 = 跑偏。数量必须少（全局 ≤ 12 条）
可协商项 Negotiable   —— 随实现调整，改动只需回写，不算跑偏
```

domi 的全局不变量（写进 `PRD-VISION.md`，非重大决策不得修改）：

```
INV-01  会话是 append-only 事件流；事件类型只增不改，历史永远可解析
INV-02  kernel 零 IO 依赖，不 import 任何 apps/* 或具体存储实现
INV-03  权限默认拒绝；每个权限决策产生一条事件，可审计
INV-04  三端不含业务逻辑，仅通过 Domi Protocol 与 daemon 通信
INV-05  Tool 是唯一执行原语；Skill 不可执行，只注入上下文
INV-06  MCP / 插件的输出是不可信数据，不是指令
INV-07  任意时刻 main 分支可运行
INV-08  真实 LLM 调用不进 CI 门禁
INV-09  Soul 是人类可读、可 diff、可否决的
INV-10  每个交付任务反向引用一条 PRD 条目 ID
```

**不变量的价值在于它少。** 12 条能记住，能在每次 review 时逐条对照。100 条等于 0 条。

### 缺口四：四个角色全是生产者，没有判官——而判官不能是 AI

谁判断"这次改动是否违反了不变量"？

**在 AI 执行的场景下，这个角色绝对不能是同一个 AI。** 自己审自己必然放水，而且放水的方式是"给出一个听起来很合理的理由"——这比直接违规更危险，因为它会说服你。

**补丁：判官是机器，人是终审。**

| 不变量 | 由谁守 |
|---|---|
| INV-01 事件只增不改 | protocol 类型快照测试（CI） |
| INV-02 kernel 零 IO | dependency-cruiser + `kernel/package.json` 依赖白名单（CI） |
| INV-03 权限默认拒绝 | 单元测试 + 默认值断言（CI） |
| INV-04 三端无业务逻辑 | 依赖边界规则（CI） |
| INV-07 main 可运行 | CI 构建 + 冒烟 |
| INV-10 任务有 PRD 引用 | 任务文件 lint 脚本（CI） |
| 其余 | 每里程碑收尾时人工逐条对照（10 分钟） |

**能自动化的不变量必须自动化。**"靠 review 守住"等于没守住。这也是 ENGINEERING.md 里三道防线的由来：物理隔离 > CI 规则 > 人工自觉。

### 缺口五：AI 执行特有的风险——上下文丢失导致的"合理偏离"

这是原流程完全没覆盖、但在 AI 执行时最致命的一条。

长任务里会话会断、上下文会被压缩。**第三天的我可能不记得第一天的架构决策，然后写出一段"看起来完全合理"的、违反 INV-02 的代码，并且给出一个很有说服力的理由。** 这不是能力问题，是机制问题——决策如果只存在于对话历史里，它就一定会丢。

**补丁：所有决策必须落盘成机器可读的约束，而不是只存在于对话或散文里。**

```
决策形态              可靠性
─────────────────────────────
只在对话里说过        会丢（几乎必然）
写在 markdown 散文里  会被忽略（下游不一定读到）
写成 ADR 条目         人能查到，但不强制
写成类型定义          编译期强制  ✅
写成 CI 规则          提交期强制  ✅
写成物理依赖隔离      根本写不出来 ✅✅
```

**每做一个架构决策，都要问一句："这条怎么变成机器能检查的？"** 变不成的，才退回写 ADR。

## 2. 关于"角色扮演"这件事的实话

角色扮演真正起作用的**不是"你现在是资深架构师"这句咒语**，而是它强制切换了**产出物的形态**。同一个模型被要求产出一份有固定章节的 SPEC，和被要求"设计一下"，输出质量天差地别——起作用的是章节约束，不是身份暗示。

**所以真正要定死的是每个角色的产出物模板，不是角色描述。** 下面是四份模板。

---

## 3. 四个角色的产出物契约

### 角色 1 · 产品专家 → `docs/prd/M{n}.md`

```md
# M{n} PRD — {里程碑名}

## 1. 本里程碑要回答的问题
（一句话。例："domi 能不能在终端里完成一次读文件→改代码→跑测试的闭环"）

## 2. 不做什么
（明确排除项，比"做什么"更防跑偏）

## 3. 需求条目
每条格式固定：

### PRD-M0-003 · 工具调用需用户确认
- **用户价值**：用户不会在无感知的情况下被改动文件
- **验收标准**：（必须可执行，见下）
  - AC-1: 调用 fs.write 时 TUI 弹出确认，拒绝后产生 tool.result{ok:false}
  - AC-2: 该决策产生一条权限事件，可在轨迹中看到
- **验收方式**：`bun test permission.spec.ts` / demo 脚本 `demos/m0-permission.md`
- **层级**：Invariant(INV-03) | Negotiable
- **优先级**：P0 | P1 | P2

## 4. 本册引用的全局不变量
（列出 INV-xx 编号）

## 5. 预算
时间预算：X 天。超出 20% 必须砍 P2，砍的决策进 ADR。
```

**两条硬规则：**

- **写不出可执行验收方式的条目，不准进 PRD。** 自然语言验收标准 = 主观验收 = 必然放水。写不出来说明需求没想清楚，回去想。
- **每册 PRD 必须有"不做什么"章节。** 这是唯一能让"砍需求"变成正式动作而不是心虚妥协的地方。

### 角色 2 · 资深架构师 → `docs/spec/M{n}.md`

```md
# M{n} SPEC

## 1. 覆盖的 PRD 条目
| PRD-ID | 由哪些 SPEC 条目实现 |
（这张表必须完整覆盖，缺一条就是设计漏了）

## 2. 取舍记录（本文档最有价值的部分）
### SPEC-M0-002 上下文拼装策略
- 候选 A：全量拼装 —— 简单，长会话会爆
- 候选 B：增量物化视图 —— 快，复杂度高
- **选 A**，理由：M0 的目标是打通链路不是性能；B 留到实测 5 万事件后再定
- 反悔成本：低（纯函数，替换一个实现即可）
- 触发重新决策的条件：合成会话压测 buildContext > 200ms

## 3. 接口契约
（TypeScript 类型 + zod schema，可直接复制进代码）

## 4. 数据契约
（事件类型、表结构、迁移策略）

## 5. 不变量影响分析
本里程碑是否触及 INV-xx？如何保证不违反？由哪条 CI 规则守？

## 6. 明确留白
（哪些地方故意不设计，等实现反馈。留白要显式，否则会变成隐性债）
```

**"取舍记录"是 SPEC 里唯一不可省略的部分。** 三个月后你会想不起来为什么选了 A，然后花两天重新论证一遍——ADR 和取舍记录就是为了省下这两天。**每条取舍必须写"触发重新决策的条件"**，否则它会变成永久的教条。

### 角色 3 · 资深工程师 → `docs/tasks/M{n}.md` + 代码

任务文件格式（纯 Markdown，git 友好，人和机器都能读）：

```md
## TASK-M0-007 · 实现权限询问链路
- status: todo | doing | blocked | review | done
- prd: PRD-M0-003
- spec: SPEC-M0-005
- 前置: TASK-M0-004
- 预估: 0.5d
- 测试先行:
  - [ ] permission.spec.ts: 默认拒绝
  - [ ] permission.spec.ts: 用户拒绝后事件正确
  - [ ] replay/m0-write-denied.json 回放通过
- 实现:
  - [ ] PermissionEngine 接口
  - [ ] TUI 确认组件
- DoD:
  - [ ] 测试全绿
  - [ ] main 可运行
  - [ ] NEXT.md 已更新
- 笔记: （中断时写在这里，恢复时先读）
```

**四条硬规则：**

1. **`prd:` 字段不能为空。** 没有 PRD 依据的任务不允许存在——这就是 INV-10，由 lint 脚本在 CI 里强制。**这条是整个防腐蚀体系里最硬的一环**：它让"顺手加个功能"在物理上无法发生。
2. **测试条目必须写在实现条目之前**，且先提交失败的测试。TDD 不靠自觉，靠文件里的顺序。
3. **任务粒度 ≤ 0.5 天**，且结束时 main 必须可跑。
4. **commit message 带 task id**：`feat(kernel): 权限引擎默认拒绝 [TASK-M0-007]`。这样 git log 本身就是进度记录，中断恢复时 `git log --oneline -20` 一眼就知道到哪了。

### 角色 4 · 测试工程师 → `docs/qa/M{n}.md`

**重新定义这个角色**：如果 TDD 真执行了，工程师已经写了大量测试。所以这一步**不是"补测试"，是"对抗性验收"**——目标是**证伪**，不是确认。

```md
# M{n} 验收报告

## 1. PRD 覆盖矩阵
| PRD-ID | AC | 验证方式 | 结果 | 证据 |
（每条 AC 必须有结论，不允许 N/A）

## 2. 不变量审计
| INV-xx | 守卫方式 | 是否生效 | 证据 |

## 3. 对抗性测试（本报告的核心价值）
不是重跑工程师的测试，而是想他没想到的失败方式：
- 边界：空会话、5 万条事件、单条 10MB 的 tool result
- 时序：工具执行中断、daemon 中途被 kill、事件写入一半掉电
- 恶意：MCP 返回 prompt injection、插件声明越权、路径穿越
- 退化：模型返回畸形 JSON、流式中断、超长思维链

## 4. 判定
PASS / CONDITIONAL PASS（列出遗留项与承诺修复的里程碑）/ FAIL

## 5. 回写建议
本轮发现的 PRD/SPEC 问题清单 → 触发回写门
```

**这个角色的独立性必须靠机制保证。** 由同一段上下文里的同一个执行体来"验收自己刚写的代码"，等于没验收。执行上：**验收必须开一个独立会话/独立 subagent，只喂 PRD + 代码，不喂实现过程的对话历史。** 不知道实现者当时怎么想的，才能问出实现者想不到的问题。

## 4. 可追溯链：整套体系的骨架

```
INV-xx  ─┐
         ├─→ PRD-M{n}-xxx ─→ SPEC-M{n}-xxx ─→ TASK-M{n}-xxx ─→ TEST ─→ QA-AC
         │        ↑                                                      │
         └────────┴──────────── 回写门 ←──────────────────────────────────┘
```

**这条链断在哪里，腐蚀就从哪里进来：**

| 断点 | 症状 | 守卫 |
|---|---|---|
| TASK 无 PRD 引用 | 顺手加功能、范围蔓延 | CI lint（INV-10） |
| PRD 条目无 SPEC 覆盖 | 需求悄悄消失 | SPEC 覆盖表必填 |
| SPEC 无 TASK 落地 | 设计了没做 | 里程碑收尾对账 |
| 验收标准不可执行 | 主观验收、放水 | PRD 模板强制 |
| 下游绕过上游 | 文档与代码脱节 | 回写门 + commit 前缀 |

**每个里程碑收尾必须做一次 10 分钟对账**：拉一张表，四列 PRD-ID / SPEC-ID / TASK-ID / QA 结论，看有没有空格。有空格就是链断了。

## 5. 可中断可继续：具体机制

三个文件，加起来每次维护 3 分钟：

**`NEXT.md`（根目录，三行）** —— 收工前必更新
```
在做: TASK-M0-007 权限询问链路
下一步: TUI 确认组件的键盘焦点处理
卡在: OpenTUI 的焦点管理 API 没查清，见 TODO(opentui-focus)
```

**`docs/tasks/M{n}.md`** —— 状态机 + 中断笔记（见上）

**git log** —— commit 带 task id，本身就是进度日志

**恢复流程固定为**（写进 README 的"开发者入口"）：
```
1. 读 NEXT.md                      （30 秒）
2. git log --oneline -20           （30 秒）
3. 读当前 TASK 的"笔记"字段         （1 分钟）
4. bun test 确认 main 是绿的        （1 分钟）
5. 开工
```

**AI 会话恢复的额外一步**：新会话必须先加载 `PRD-VISION.md`（不变量）+ 当前 `SPEC` + 当前 `TASK`。**不加载这三份就开始写代码，是"合理偏离"最主要的发生场景。** 建议把这条写成仓库里的 `CLAUDE.md` / `AGENTS.md`，让工具自动加载。

## 6. 每一轮的流转规则

```
┌─────────────────────────────────────────────┐
│ PM      写 PRD/M{n}.md                       │
│         门禁：每条 AC 可执行？有"不做什么"？   │
├─────────────────────────────────────────────┤
│ ARCH    写 SPEC/M{n}.md                      │
│         门禁：PRD 覆盖表完整？取舍有反悔条件？ │
│         门禁：触及的 INV 都有 CI 守卫？        │
├─────────────────────────────────────────────┤
│ ENG     写 TASKS + TDD 实现                  │
│         门禁：每个 TASK 有 prd 引用？          │
│         门禁：失败测试先提交？main 一直绿？    │
├─────────────────────────────────────────────┤
│ QA      独立会话，对抗性验收                  │
│         门禁：每条 AC 有结论？INV 逐条审计？   │
├─────────────────────────────────────────────┤
│ 复盘    对账 + 回写 + 更新不变量 + 下册 PRD   │
└─────────────────────────────────────────────┘
        ↑                                    │
        └──────── 回写门（任意环节可触发）─────┘
```

**每一环的门禁不过，不准进下一环。** 门禁是清单，不是感觉。

## 7. 回到那个问题：够不够？

**原方案（四角色串行）**：能防住"想不清楚就动手"，防不住"想清楚了慢慢偏"。

**补齐五个缺口后**：

| 腐蚀方式 | 守卫 |
|---|---|
| 想不清楚就动手 | 四角色 + 门禁清单 |
| 范围蔓延、顺手加功能 | TASK 必须引用 PRD（CI 强制） |
| 文档与代码脱节 | 回写门 |
| 架构慢慢腐化 | 不变量 + 机器守卫（物理隔离 > CI > 人工） |
| 自审放水 | QA 独立会话，只给 PRD 不给实现历史 |
| AI 上下文丢失导致合理偏离 | 决策落盘为类型/CI 规则；新会话强制加载三件套 |
| 探索性需求写死在瀑布里 | PRD 分册，每里程碑一轮 |
| 不敢砍需求 | PRD 必填"不做什么" + 预算超 20% 强制砍 |

**剩下一个守不住的**：**你自己的兴趣衰减。** 没有任何流程能防住这个。唯一有效的对策是让每个里程碑都有一个**能拿出去给人看的东西**（M0 是终端里跑通的一段 demo，M1 是一张 GIF）。流程保证不腐蚀，可见的进展保证你还想继续——两者缺一不可。

不是写 M0 的 PRD，是先把这四样东西建起来（约半天）：

1. `PRD-VISION.md` —— 3 页，只有不变量和一句话定位
2. `docs/prd|spec|tasks|qa/` 四个目录 + 四份模板文件
3. `NEXT.md` + `docs/adr/000-template.md`
4. `AGENTS.md` —— 告诉 AI 每次开工必读哪三份文件

**模板先于内容。** 先有模板，第一册 PRD 才不会写成散文。
