# 011 MCP 推迟到 M3

- 日期：2026-09-14
- 状态：已采纳
- 上位：`docs/adr/010` §「已知风险：MCP SDK 的版本分裂」· `docs/prd/M2.md` §5.1

**Context**：ADR-010 把「MCP SDK 版本」列为进入 M2 前必须拍板的一条，并列了三条路：
① 用 v2.0.0-beta 并钉死版本；② 用 v1 但回写降级 `PRD-M2-001` 的 AC；③ MCP 整体推到 M3。
`docs/prd/M2.md` §5.1 倾向 C，但注明「这条必须你拍」。

2026-09-14，用户拍板：**「MCP 我暂时用不上。可以放到 M3。或者直接用 beta 版本。」**

两个选项里取哪个，判据不是技术优劣而是**需求存在与否**：
现在没有要接的 MCP server，为一个用不上的能力去背 beta 的破坏性变更税（`RECON-DSH` §1 记过 DSH 钉 rc 的代价），
是先付钱后确认需求。所以取 C；beta 作为**保留退路**，等真有 server 要接时再按下面的条件重新评估。

**Decision**

1. `PRD-M2-001`（MCP client）与 `PRD-M2-009`（内置 MCP server 清单：browser use / computer use）**移出 M2，进入 M3**。
   AC 原文**不改**——这是排期调整，不是范围降级。
   **ID 也不改**：`PRD-M2-001` 这个编号继续用，尽管它现在住在 M3。
   重编号会让所有既有引用（spec、任务、ADR、commit message）一起失效，
   而编号的用处本来就是**指向同一条需求**，不是标记它在哪个里程碑。
2. M2 的范围收敛为：M2-002 确定性清理 · M2-003 LLM 压缩 · M2-004 L2 检索 ·
   M2-005 轨迹显示 · M2-006 注入防护 · M2-007 schema 迁移 · M2-008 L1 回放。
3. M2 预算由 19 天下调为 **14 天**（移出的两条按 `PRD.md` 原估合计 5 天）。
4. `docs/adr/010` 表里「computer-use MCP server 选哪个」的时点随之从 M2 改为 M3。

**触发重新决策的条件**（任一成立就回到这条 ADR 重评，不要临时决定）：

- 出现一个**具体**要接的 MCP server（不是"以后可能要接"），且它只有 2026-07-28 规范的实现；
- `@modelcontextprotocol/sdk` v2 GA——那时三条路里的风险项消失，按正常选型走即可；
- 进入 M3 时，无论上面两条是否发生，都必须在 M3 的批准门上把这条重新过一遍。

**Consequences**

- 好处：M2 专注在两个验证过的生态真空（轨迹面板、确定性压缩）上，不被上游版本分裂拖住。
  实际结果是 M2 的七条里已经交付六条（M2-002/005/006/007/008 + 部分 M2-003），只剩 M2-004。
- 代价：**demo 的完整度下降**——没有 MCP 就没有 browser use / computer use，
  「功能齐备的 Agent」这句话在 M2 结束时还不成立。这是明知的取舍，不是疏漏。
- `PRD-VISION.md` §6 第一类（browser/computer use 全部收敛为 MCP server，domi 零实现）的结论不变，
  只是兑现时点从 M2 挪到 M3。
