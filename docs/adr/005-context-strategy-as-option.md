# 005 上下文拼装策略改为可选项，压测从 M0 门禁降级

- 日期：2026-09-14
- 状态：已采纳

**Context**：`SPEC-M0-002` 选了"先全量拼装"，并把"5 万事件 > 200ms"写成触发重新决策的条件；`PRD-M0-007` AC-2 据此硬要求 `docs/adr/002-buildcontext-perf.md` 里有实测毫秒数。实际推进时决定先跳过这次压测——M0 的目标是打通链路，性能问题还没有真实会话来定义"多长算长"。

**Decision**：把"全量 vs 增量"从**一次性取舍**改为**运行期可选项**：`ContextPolicy.strategy` 默认 `'full'`，策略经注册表挂载，`'incremental'` 先占位并在调用时明确报错。压测降级为可选（`TASK-M0-002` 不再是 M0 门禁），`PRD-M0-007` AC-2 相应回写。

**限定**（这条是本 ADR 的重点，不是附注）：option **只是注册点，不是两套实现**。M0 只实现 `'full'`。在拿到真实会话的性能数据之前不写 `'incremental'`——否则就是没有数据却养了两条都要维护、都要测、谁也说不清哪条对的路。

**Consequences**：换来的是不必为一个还没发生的性能问题停下来做测量，且将来加增量实现是**挂一个策略**而不是改 `buildContext`，反悔成本从"中"降到"低"。付出的代价有三项，写在这里免得以后假装没有：
1. **少了一个数字**。原来的触发条件"> 200ms"是可判定的；现在没有基线，"要不要上增量"退回成主观判断。缓解：`TASK-M0-022` 的 M0 DoD 走查时，用 demo 产生的真实会话补一次量，数值写回本 ADR 的 `## 实测` 段。
2. **多了一个可配置面**。配置项越多，"用户配错了"和"两条路行为不一致"就越可能。缓解：`'full'` 是唯一默认，文档不鼓励改；增量实现落地时，验收标准是**它的输出与 `'full'` 逐字节相同**（`'full'` 是正确性基准，这一条原 SPEC 已经写了，现在它变成了硬约束）。
3. **策略注册表本身是新代码**，它在 M0 没有第二个使用者，属于为将来付的首付。接受，因为它同时是 M2 压缩策略 A/B 的挂载点。

## 触发重新激活压测的条件

① 真实会话里 `buildContext` 单次耗时被感知到（TUI 出现可见卡顿）；
② 会话事件数超过 2 万；
③ M2 要做压缩策略 A/B 时——那时需要基线数字。

三条任一满足即补测，并把实测值写回本 ADR 的 `## 实测` 段（届时新增）。
