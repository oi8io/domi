# 029 上下文不变量：投影决定即事件 + 前缀只增不改（INV-12 加强为两款）

- 日期：2026-10-08
- 状态：已采纳（用户 2026-10-08 拍板「这是必须的，尤其是 Soul 或者 Memory 这些都是需要新会话冻结的」；依据 `docs/RECON-CONTEXT.md` R0 / E2–E4）
- 修改：`PRD-VISION.md` §5 INV-12（v1.1 → v1.2）；`docs/adr/019` 的「更新立即生效」改为「下一个会话生效」

**Context**：上下文调研（`docs/RECON-CONTEXT.md`）用真实会话库量出来一件事——**只追加时，两次请求之间的缓存损失平均只有 4 token；全部有意义的损失都来自「改历史」**：

| 改历史的地方 | 实测每次丢的缓存 |
|---|---|
| 计划更新：计划文本拼在本轮 user 消息末尾，计划一变，本轮之后的内容全部重算 | 30.6k tok |
| `verify.required`：动态层「搬家」到新的 user 消息 | 41.8k tok |
| 新的一轮：上一条 user 消息的动态尾巴被拿掉 | 14.2k tok |

另外三处是同一类问题，只是这批样本里还没触发：Soul 每 5 轮后台改一次、立刻进 system；规矩文件与技能清单每一步现读；`clean` 策略在同一调用第二次出现时**回溯**把第一次的结果换成指针。

这类错误有两个特点，决定了它必须是不变量而不是实现细节：
1. **横切**：任何以后加进上下文的东西（插件层、项目记忆、环境块、MCP 资源）都可能再犯一次；
2. **静默**：运行时只表现为「命中率莫名其妙低一点」，不报错、不崩，单测也测不出来（单测只看一次请求）。

ADR-005 / INV-02 已经保证了「同一事件流拼出同一份上下文」的**确定性**，但没保证**随时间的稳定性**——前者说的是同一时刻重放两次结果一样，后者说的是第 n+1 次请求不得改写第 n 次已经发过的部分。缺的是后者。

**Decision**：INV-12 从一句话加强为两款，仍占一个编号：

> **INV-12 上下文是事件流的投影，只增不改。**
> (a) **投影决定即事件**：压缩、清理、遮蔽不销毁原始事件；它们的**决定本身**是追加的事件（`ctx.compact` / `ctx.cleanup` / `ctx.mask` …），上下文只由事件流与配置算出，不在请求时现场判断「哪些该删」。
> (b) **前缀只增不改**：同一会话里，后一次发给模型的请求必须以前一次请求为前缀（工具定义、system、历史消息逐字节相同）。例外只有：压缩点、用户显式的刷新（信任仓库、换模型、手动刷新上下文）。Soul、记忆、项目规矩、技能清单、工具表**在会话开始时定格**，会话内的变化在下一个会话（或下一个压缩点）生效；会话内必须让模型知道的变化（计划、环境、验证提示、运行中补充），以**追加**的方式送达，不改已发出的消息。

守卫（CI）：**前缀稳定性回放**——L1 回放一组 fixture（含计划更新、`verify.required`、运行中补充、新一轮、Soul 改动、同一文件读两次），对每一对相邻请求断言「前一次是后一次的前缀」，两者之间有压缩点或显式刷新事件的除外。它同时守住 (a)：只要有一种投影会回溯改写，这条就红。运行期另有观测：每次请求记前缀指纹，断裂时落事件并在上下文 tab 显示断在哪一层（RECON O1）。

**考虑过的另一种做法**：新增 INV-14、同时把 INV-08（真实 LLM 调用不进 CI）并入 INV-13 以守住「活跃 ≤ 12 条」。**拒绝**：INV-08 在文档与代码注释里被引用 40 多处，合并会让这些引用指向一个占位编号；而 (a)(b) 本来就是同一件事的两面（(a) 是空间上的「投影只读事件」，(b) 是时间上的「投影只往后长」），守卫也是同一条测试，放在一个编号下更准确。活跃条数仍为 12。

**Consequences**：
- **Soul / 记忆生效时间变了**：ADR-019 的「更新立即生效（否则 Soul 永远等人）」改为「写入立即落盘、**下一个会话**生效」；事后审阅不变。界面要明示「将在新会话生效」，并给「刷新上下文」入口（显式刷新付一次缓存未命中，用户自己选）。
- **动态层改形**：`builtin.workspace` / `session.plan` 不再拼进最后一条 user 消息；计划与环境的变化落成追加事件，渲染为新的 user 块（Manus 的 todo.md「复述」同理：越靠后注意力越强，且不改历史）。代价是计划文本会在历史里重复出现多次——只在变化时追加，压缩时折叠。
- **`clean` 要重写**：去重、已解决错误的折叠改为在边界点（压缩点或固定步距）对冷区一次性做出决定并落事件；热区与已发出的部分不再变。
- **L1 fixture 要重录**：请求形状变了，升 `SCHEMA_VERSION`，补 legacy fixture；旧会话按旧投影可解析（INV-01）。
- **服务端上下文能力**（Anthropic compaction / clear_tool_uses）天然违反 (b)——它们在服务端改历史。按用户拍板 4，它们走厂商适配层、**默认关**，打开时视为「每次触发都是一个压缩点」，并在事件流里记下服务端报告的 `applied_edits`，保住 (a) 的可追溯。

**触发重新评估的条件**：主流厂商提供了「改中间某段而不失效后续缓存」的能力；或用户反馈「改了 Soul / 规矩要开新会话」明显影响使用（届时考虑把显式刷新做得更顺手，而不是放宽不变量）。
