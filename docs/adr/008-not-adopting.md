# 008 决定**不**引入：Turborepo / CLI 解析库 / 日志库 / tokenizer

- 日期：2026-09-14
- 状态：已采纳

**Context**：`DESIGN.md` §5 与后续需求里出现过这四个候选。**"决定不引入"也是决策**——不落盘的话，每隔几周就会被重新提起一次，而且每次都要从头论证。

**Decision**：四项全部不引入。逐条写明理由与**何时重新评估**：

| 候选 | 不引入的理由 | 触发重新评估的条件 |
|---|---|---|
| **Turborepo** | 5 个包，`bun test` 全量 3 秒，`pnpm check` 全量不到 10 秒。任务编排与缓存在这个规模下是纯负担 | `pnpm check` 全量超过 **60 秒**；或 CI 需要跨机远程缓存 |
| **CLI 解析库**（commander / citty） | 用 Node/Bun 内置的 `util.parseArgs`。M0 只有一个入口命令，引一个库是为将来的想象付费 | 子命令超过 **8 个**；或需要自动补全 / 自动生成 help |
| **日志库**（pino） | **事件流本身就是结构化日志。** 再上一套 logger 会立刻产生"同一件事记两遍、两边还不一致"的问题；`PRD-M1-009` 的诊断信息应当从事件流投影出来，不是另起炉灶 | M3 拆 daemon 后出现**与会话无关**的进程级日志需求（启动、端口、连接生命周期）——那时它和事件流确实是两种东西 |
| **tokenizer**（js-tiktoken / gpt-tokenizer） | 先用 provider 返回的 usage——ADR-004 已经要求原样透传。本地 tokenizer 与服务端计数天然对不齐，拿它做状态栏只会显示一个"看起来精确的错数" | 需要在**发送前**预估 token（M2 的压缩点选择）。届时只在 `packages/memory` 引入，且必须标注它是估算值，不得覆盖 usage 的真值 |

**Consequences**：换来更小的依赖面与更少的"这个库怎么用"的上下文开销。代价是上面四项各自在触发条件到来时要补一次工作——但那时需求是具体的，选型会更准。

**这四条不是"永远不用"，是"现在的证据不支持"。** 重新评估时请直接改本 ADR 的状态，不要新开一条讨论。
