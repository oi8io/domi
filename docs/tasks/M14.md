### BUG-M14-001 · token 估算按「字符数 / 4」，中文低估 3–4 倍
- status: fixed（`@domi/protocol` 的 `estimateTextTokens` 统一四处口径；复现测试 5 红 → 绿）
- 现场: 全仓的 token 估算都是 `length / 4`——`kernel/build-context.ts` 的 `estimateTokens`（maxTokens 超长报错）、`kernel/loop.ts` 的 `model.request.ctx.tools/history`、`prompt/layer.ts` 的 `approxTokens`（层清单、`domi prompt dump`、上下文 tab 分段）、`memory/cleanup.ts` 的 `approxTokens`（压缩 / 清理前后 token 与节省量）。
  `JSON.stringify` 不转义汉字，一个汉字只算 0.25 token；实际各家分词器约 0.7–1.5。一份 2812 字（中文 1591）的 soul.md 按旧口径约 700，实际约 1.5k–2.5k。
  后果：中文为主的上下文 maxTokens 守卫放行了本该报错的请求（模型侧 400）；上下文 tab 各段偏小、「未归类」被撑大；压缩记录的前后 token 偏小。违反「统计数据必须真实」（2026-10-05 拍板）。状态栏总量走 model.usage，不受影响。
- 修法: `@domi/protocol` 加 `estimateTextTokens(text)`（CJK 每字 1、其余每 4 字符 1，向上取整），上面四处统一改用它；不引 tokenizer（ADR-008）。口径已回写 SPEC-M14-006 取舍-1。
- 测试: kernel/test/build-context.spec.ts、kernel/test/context-loop.spec.ts、prompt/test/layering.spec.ts、memory/test/cleanup.spec.ts「BUG-M14-001」
- 笔记: 附件段（client-core `size/4`）不改——拿到的是字节数，UTF-8 汉字 3 字节约 0.75 token/字，同量级（SPEC 已注明）。
  `memory/test/compactor.spec.ts`「短会话压了反而更大」原来的前缀在旧口径下才算「短」，换成真正短的前缀（断言的道理不变）。
  `.api.md` 只多了 `estimateTextTokens` 一个导出，事件 schema 未变，旧事件照常解析。
