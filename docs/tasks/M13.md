## 实现笔记（2026-09-24）

- **协议多了一个字段**：`user.input.noteIds`（可选）——正常收场后才到的补充由 daemon 拼成下一轮的 user.input，
  端上凭它把本地排队的补充认作「已送达」，不然重连对账会把它当退回、在输入框里重复出现。SPEC-M13-001 取舍-4 已补记。
- **daemon 的 ActiveTurn 从占住「忙」那一刻就建好**（不是等宿主开跑）：校验窗口里来的补充也能排上；
  校验失败 / 还没开跑就被中断 → 按异常收场退回。
- **kernel 的三个检查点只看外部 signal**；所有 `stop()` 现在都写 `error.stopReason`，中断时再带 `by`。
  没开始的调用补 `interruptedResult`（reason = interrupted），不是 `notRunResult`。
- **spawn 子 agent 接上了 ctx.signal**（原来不看 signal，父轮中断要干等子 agent 跑完）。
- **Web 的旧测试改了口径**：`render.spec` 里「忙的时候发送按钮不可点（PRD-M3-004 AC-3 的前端那一半）」
  改为「忙的时候发送变成补充」（PRD-M13-001 AC-9）。daemon 侧 `session.submit` 忙时仍回 SESSION_BUSY，M3-004 AC-3 本身不变。

## 缺陷与待优化登记

### BUG-M13-001 · `domi data purge` 在含符号链接环的目录上 ELOOP 崩溃（目录统计）
- status: 已修（TASK-M13-009，2026-10-05）
- 现象: `~/.domi/worktrees/<hash>/s-<session>/node_modules`（隔离工作树会话里 pnpm 装的依赖）含符号链接环时，`data purge` 抛 `ELOOP: too many symbolic links`，确认清单打不出来；`pnpm check` 的 `data > purge` 测试在本机红（CI 因 HOME 干净而绿）。
- 根因: `packages/cli/src/data.ts` `dirSize()` 用 `statSync`（跟随符号链接）+ 无防护递归；pnpm workspace 为互相有 dev 依赖的本地包（`@domi/kernel ↔ @domi/capability`）建双向符号链接，形成目录环。Node 模块解析靠 realpath 去重，项目正常；盲目递归的遍历代码不设防。
- 违反: PRD-M1-010 AC-2（purge 执行前必须列出目录与总大小）。
- 修法: `dirSize()` 改用 `lstatSync`（不跟随符号链接，链接按自身计、不进递归）；purge 测试隔离 HOME。见 TASK-M13-009。

### BUG-M13-002 · ctx% 用的是全会话累计输入，累计过窗口就永远 100%；自动压缩同口径，过阈值后每轮都压
- status: done
- `aggregate` 把每次请求的 input + cacheRead 累加后除以 `context.maxTokens`。每次请求都会重发整段上下文，累计值是「花了多少输入」不是「窗口里装了多少」。现场 53 次请求累计 2572.9k ÷ 150k → 截成 100%，而 build-context 的超窗检查一次没报，说明实际占用一直在窗口内。违反 PRD-M1-007 AC-2「上下文占用」。`maybeAutoCompact` 用 input + output 累计比阈值：`strategy: compact` 时过了 70% 就每轮触发，压完累计也不降。
- 修法：新增 `contextTokens` = 最近一次 `model.usage` 的 input + cacheRead；`ctx.compact` 之后、下一次请求之前按 tokensBefore − tokensAfter 往下扣。ctx% 与自动压缩都用它。见 TASK-M13-010。

### BUG-M13-003 · 缓存读一个都没读到，命中率恒 0%、花费按全价算
- status: done
- `readUsage` 认的是 Anthropic 式字段（input 不含缓存）。AI SDK 7 的 finish-step 里 `inputTokens` 是**含缓存的总输入**，缓存读在 `inputTokenDetails.cacheReadTokens`；openai-compatible 只认 `prompt_tokens_details.cached_tokens`，DeepSeek 原生的 `prompt_cache_hit_tokens` 只在 `usage.raw` 里。结果 cacheRead 恒 0、命中被算成全价输入。Anthropic 原生的 `cache_creation_input_tokens` 也没算进提示词。
- 修法：`readUsage` 归一为「input = 没走缓存读的输入（含缓存写），cacheRead = 缓存读，两者之和 = 这次的提示词」，认 AI SDK 7 / 5、OpenAI、DeepSeek、Anthropic 五种形状，缓存读缺失时回落到 provider 原文。用量页（`summarizeUsage`）与预算共用这一份，一起变对。

### BUG-M13-004 · tok/s 的分母含工具时间，单步的一轮显示不出来
- status: done
- loop 把一步的 request / delta / usage / tool.call 攒到流结束一起落盘，共用一个 ts：request 的时间其实是这一步结束的时间。tok/s 的分母是「本轮第一次 request 的 ts → 最后一条事件」，即从第一步**结束**算起、含所有工具执行与等确认的时间；只有一步的轮分母是 0，显示不出来。
- 修法：`model.request` 开流前单独落盘；tok/s = 本轮各步输出之和 ÷ 各步「request → usage」耗时之和（含首 token 延迟，不含工具）。老会话请求与用量同 ts，量不出来就是 null，不编数。

### BUG-M13-005 · 工具次数是端上自己数的，分页 / 重连后少算，和 steps 对不上
- status: done
- 状态栏的工具次数取 `status.toolCalls`（client-core 收到 `tool.call` 才 +1），steps 却是 daemon 全量聚合的。打开旧会话只加载尾部窗口，前面的工具调用没数到——现场 53 steps 对 6 tool calls。
- 修法：metrics 推 `toolCalls`（`aggregate` 本来就算了），`setMetrics` 以它为准，两次推送之间仍实时 +1；老 daemon 不推就保留端上计数。
