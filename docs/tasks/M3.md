## 缺陷与待优化登记

> 用户定的规矩（2026-09-15）：**先做主线**；体验类的优化记在这里，确实是缺陷的按缺陷修（先写复现测试）。
> 状态：open | fixed | wontfix | recorded（只记录，不排期）

### BUG-M3-001 · 思考过程一个 token 一行
- status: fixed（client-core store：紧挨着的 reason 片段拼成一段，与 delta 同一个规则）
- 现场: Web / TUI 里思考逐字换行，没法读
- 测试: client-core/store.spec.ts

### BUG-M3-002 · `domi session restore <id>` 是空操作
- status: fixed（CLI 调用 `SessionRepo.restore`；不存在的 id 报错并返回 1）
- 现场: packages/cli/src/run.ts 只打印「已恢复」，没有调用 `SessionRepo.restore`
- 顺带: `dataDir()` 先看 HOME——Bun 的 os.homedir() 不跟随运行期对 HOME 的修改，原来的 CLI 测试其实读写的是真实的 ~/.domi

### BUG-M3-003 · 状态栏缺「本轮耗时」
- status: open（M1 遗留）
- 现场: PRD-M1-007 AC-1 点了名；kernel 的 `TurnResult.counters.elapsedMs` 有数，没进 metrics。TUI 与 Web 都没有

### BUG-M3-004 · anthropic base_url 不带 /v1 时请求打到错误路径
- status: fixed（1e1cd35）
- 现场: `https://api.z.ai/api/anthropic` → 「No output generated」

### BUG-M3-005 · provider 出流前抛的错被吞，用户什么都看不到
- status: fixed（19e3612）

### BUG-M3-006 · `[model.capabilities]` 从未被读取，openai-compatible 网关永远用不了工具
- status: fixed（19e3612）

### BUG-M3-007 · 打不开会话一律报 SESSION_NOT_FOUND；失败后会话永远忙
- status: fixed（e4e9248）

### BUG-M3-008 · 两个进程同时接管同一把陈锁
- status: open（已知限制）
- 现场: 都读到死进程的锁 → A 删锁建新锁 → B 再删掉 A 的新锁 → 两个都以为自己赢了。
  需要「持有者已死」与「删除」之间的原子性（比如先 rename 到唯一名再删）

### BUG-M3-009 · 切换模型只改了一个字符串，请求照旧发给旧模型
- status: fixed
- 现场: AiSdkProvider 构造时就绑死了模型名，不看请求里的 model；DomiSession.switchModel 只改 currentModel。
  PRD-M1-002 的测试用的是替身 provider，看不出来。现在切换时按新的 provider/模型重建实例（注入的替身除外）

### BUG-M3-010 · 分支会话拼上下文时不读父链
- status: open
- 现场: store 有 fork / readLineage（PRD-M1-006 AC-3），但 kernel 的 runTurn 用 `sink.read(sessionId)`，
  分支会话的模型看不到分叉点之前的任何历史。目前没有任何入口能建分支，所以还没人撞上

### BUG-M3-011 · `domi data export` 导出的是配置**模板**，不是用户自己的配置
- status: fixed（改 YAML 时一起修：读用户的配置文件，去掉 api_key 后导出；没有配置文件才导出模板）
- 现场: run.ts 调 `exportAll(log, out, CONFIG_TEMPLATE)`。PRD-M1-010 AC-1 要的是「导出全部会话事件流与配置」

### BUG-M3-012 · 配置里的提示词层从来没被读取
- status: open（M1 遗留）
- 现场: `domi prompt dump` 调 `layersFromConfig([])`，ConfigSchema 里也没有 `prompt` 这一节。
  PRD-M1-005 AC-3「用户可在配置文件中覆盖或追加层」实际上没有入口；runtime 拼上下文时同样不读

### OPT-M3-006 · 跨 provider 切换沿用同一套凭据
- status: recorded
- 说明: 配置里只有一套 key / base_url。`/model qwen openai-compatible` 会拿 anthropic 的 key 去打另一个端点。
  要真的「Claude 想、本地 Qwen 跑」，配置得支持多个具名 provider

### OPT-M3-001 · 每个 token 一条事件
- status: recorded
- 说明: model.delta / model.reason 逐 token 落库、逐 token 推送。事件库体积与推送量都随 token 数线性增长。
  合并落库会改变「事件即真相」的粒度，要和 L1 回放、压缩一起想，不是 UI 层能修的

### OPT-M3-002 · 代码更新后，已在跑的 domid 还是旧代码
- status: recorded
- 说明: `domi` 会复用在跑的 domid。握手里有 serverVersion，可以在不一致时提示重启（或自动重启空闲的 domid）

### OPT-M3-003 · 没有客户端在线时，询问会一直等
- status: recorded
- 说明: 这是有意的（不替人答），但任务会无限期挂着。可以考虑超时后按拒绝处理并落一条事件

### OPT-M3-004 · Web 包 327KB，大头是 zod
- status: recorded
- 说明: client-core 只用到 protocol 的类型与 PROTOCOL_VERSION，却把整张 zod 方法表打进了浏览器包

### OPT-M3-005 · daemon 里 submit 的异常仍会被静默吞掉
- status: recorded
- 说明: BUG-M3-005 修掉了最常见的来源（loop 收住了 provider 的异常），但 runtime 其它地方抛的错
  仍只被 `.catch(() => undefined)` 吞掉；至少应写进 domid.log
