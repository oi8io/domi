# M13 PRD — 运行中对话：补充与中断

## 1. 本里程碑要回答的问题

**agent 在跑的时候，用户能不能继续说话？** 两种说话方式：

- **补充**：不停下来，把话带给正在干活的 agent，**下一步**生效（「顺便把测试也跑一下」「文件在 src/ 下，不在 lib/」）
- **中断**：停下这一轮（发现方向错了），停下后接着说新的话

现状两样都没有：跑的时候输入框是禁用的，也没有任何停下来的入口。

## 2. 拍板（2026-09-24，全部定案）

| # | 疑点 | 定案 | 影响 |
|---|---|---|---|
| a | 补充 / 中断 / 打断并发送三样都做？ | **补充 + 中断**。补充 P0；中断 P1（承接 M11-007，Web + TUI 同做）；**打断并发送不做**（用户先中断、再发送，两步） | 001 / 002；§4 |
| b | 运行中按回车的默认行为 | **回车 = 补充**；中断是显式动作（Web：发送键旁的「停止」；TUI：`Esc`）。误触代价：补充最多多一句话，中断会丢掉进行中的工作 | 001 / 002 |
| c | 这一轮异常收场（出错 / 护栏 / 用量上限 / 中断）时还没送达的补充怎么办 | **退回发送端的输入框草稿**，不自动开下一轮——出错后自动跑是人的决定，不是系统的（与 recovery「不自动接着跑」一致） | 001 AC-7 |
| d | 补充能带什么 | **首版只收纯文本**（按起草建议，未单独问），不带附件 / 引用 / 技能（要带就等这一轮结束正常发） | 001 AC-1 |
| e | 中断语义（M11-007 一直卡在「终止方案 S1–S4」，但 S1–S4 在仓库里没有任何记录） | **停这一轮，不退出**：已生成的内容保留；正在跑的工具收到中止信号；没执行完的工具调用补 `tool.result{ok:false, reason:'interrupted'}`；落这一轮的结束标记；**不自动续跑**，由 M12-004 AC-10 的「计划还剩 N 步 · 继续」接手 | 002 |

## 3. 现状核查（2026-09-24 在代码里核实）

| # | 事项 | 现状 | 结论 |
|---|---|---|---|
| 1 | 运行中能否发送 | Web `Composer.tsx` 发送键 `disabled={busy \|\| pending}`；TUI `<Prompt disabled={busy}>`；daemon `session.submit` 忙时回 `SESSION_BUSY`（PRD-M3-004 AC-3），理由写在 `core.ts` 文件头：「排队让用户以为没发出去，丢弃让他以为发出去了」 | 补充走**新 RPC**，`session.submit` 的忙时语义不改（M3-004 AC-3 不划）；排队的顾虑用「看得见的队列状态」化解（001 AC-5） |
| 2 | loop 能否在中途吃进新输入 | `kernel/src/loop.ts` `runTurn` 每一步开头 `deps.sink.read(sessionId)` 重读**整条事件流**再 `buildContext`——事件流里多出来的用户内容，下一步自然进上下文 | **架构天然支持**，改动集中在「在哪个点、由谁写入」 |
| 3 | 写入时机的约束 | 一步里 `tool.call` 整批落盘后，`tool.result` 逐个追加；provider 要求 tool_use 后紧跟 tool_result。daemon 收到就直接追加的话可能插在两者之间 → 下一次请求被 provider 拒 | 补充**只能由 loop 在安全点取走并落盘**（001 AC-2） |
| 4 | 模型写最终回答时 | 本步无工具调用 → `beforeComplete` 后直接 `return completed` | 需要在收场前再查一次队列，有就再跑一步（001 AC-3） |
| 5 | 「轮」的语义 | `user.input` 是轮边界：`paginateByTurns`（M11-009）、引用本轮、分支点、`planProgress` 的 interrupted 复位、标题取首条输入 | 补充**不能复用 `user.input`**，另开事件类型（001 AC-1） |
| 6 | 中断 | 协议里没有会话级中断 RPC（只有 `task.cancel`）；`runTurn(deps, id, input, signal?)` 已接受外部 `AbortSignal`，内部 `AbortController` 传给 provider 与 `tools.run`；流中断时已生成的 `produced` 仍会落盘；`recovery.ts` 已有 `reason:'interrupted'` 的补结果与结束标记逻辑 | 底座都在，缺 RPC、runtime 接线、两端入口（002） |

## 4. 不做什么

- **不改 `session.submit` 的忙时语义**：它仍回 `SESSION_BUSY`；补充是另一个意图、另一个 RPC
- **补充不是回答**：等权限确认 / 问题框（`ask.user`）时，补充不能当作回答，也不能改变权限决策（INV-03）；它照常排队，等那个工具返回后的下一步送达
- **不给子 agent / 并行子任务送补充**：只进会话主循环；子 agent 由主循环在下一步自行决定要不要转达
- **不做轮内「撤回已送达」**：送达 = 已写入事件流 = 模型已看到（INV-01 只增不改）；送达前可撤回
- **首版补充不带附件 / 引用 / 技能**（疑点 d）
- **中断后不自动续跑**，也不自动重试被中止的工具
- **不做「编辑排队中的补充」原地修改**：撤回再发即可
- **不做「打断并发送」组合动作**（拍板 a）：中断后输入框可用，用户再发送即可；想以后做，建在 PRD-M13-002 上，不需要新语义

## 5. 需求条目

### PRD-M13-001 · 运行中补充（排队，下一步送达）

- **用户价值**：agent 跑着的时候想起要补一句，不用等它跑完、也不用打断它——补充在它下一步开始前送到，它带着新信息继续干
- **说明**：
  - 新 RPC（暂名 `session.note`）：会话**忙**时进 daemon 内存队列，回 `{ state: 'queued', noteId }`；会话**闲**时等同一次正常提交，回 `{ state: 'submitted' }`——「查忙闲 + 入队 / 提交」在 daemon 里原子完成，不留「这一轮刚好结束」的竞态窗口
  - 送达 = loop 在**安全点**把队列里全部补充按发送顺序取走，写成新事件（暂名 `user.note`），再拼上下文发下一次请求。安全点只有两个：①每一步开头（上一步的 `tool.result` 已全部落盘）②模型要收场前
  - 进上下文时是一条用户消息，带「运行中补充」标记，让模型知道这是中途插话而不是新任务
  - 队列在 daemon（不在端上），多端看到的是同一份
- **验收标准**：
  - AC-1: 新事件类型 `user.note`（`text` 必填，首版只收文本）；协议只增不改（INV-01），旧端不认识时按未知事件跳过不崩
  - AC-2: 补充只在安全点落盘：事件流里任何 `tool.call` 与它的 `tool.result` 之间不会出现 `user.note`；`buildContext` 产出的消息序列里 tool_use 后紧跟 tool_result（kernel 单测：假 provider 一步发 3 个工具调用，第 1 个执行中入队补充 → 断言补充落在第 3 个 `tool.result` 之后、下一次 `model.request` 之前）
  - AC-3: 模型本步没有工具调用、准备收场时，队列非空 → 先送达补充并再跑一步，而不是结束这一轮；这一步照常受 `loop.maxToolCalls` / 墙钟护栏约束
  - AC-4: `user.note` 不是轮边界：分页（`paginateByTurns`）、引用本轮、分支点、标题生成都不把它当新的一轮；`planProgress` 的「被打断」复位规则 SPEC 列清单逐项定
  - AC-5: 看得见：发送后输入框上方出现排队条（「排队中 · 下一步送达」+ 条数），送达后排队条消失、补充以用户气泡（带「补充」标识）出现在对话里它**真实被模型看到的位置**；多端同步（新通知，暂名 `session.notes`，推送当前队列）
  - AC-6: 送达前可撤回（按 `noteId`）；已送达的撤回返回「已送达」且不产生任何事件
  - AC-7: 这一轮异常收场（`stream_error` / 护栏 / 用量上限 / 中断）时仍在队列里的补充不丢不自动跑：退回发送端（输入框草稿恢复原文），其他端的排队条同步消失（疑点 c）；daemon 进程挂掉时队列随进程丢失，端上凭本地副本恢复草稿
  - AC-8: 等权限确认或问题框时入队的补充不影响那次确认 / 回答（INV-03），在那个工具返回后的下一步送达
  - AC-9: 两端入口：Web 与 TUI 运行中输入框**不再禁用**，回车 = 补充（疑点 b）；闲时回车行为与现状完全一致（回归）
  - AC-10: 评估回放（INV-13）：带 `user.note` 的会话按录制位置重放，补充在同一步送达
- **验收方式**：kernel loop 单测（安全点、收场前再跑一步、护栏计数）+ `buildContext` 单测（tool_use/tool_result 相邻性）+ daemon 单测（忙闲原子判定、10 客户端并发入队顺序、撤回、异常收场退回）+ paginate 单测（`user.note` 不切轮）+ client-core store 单测 + Web SSR / TUI 组件测试（排队条、补充气泡）+ 协议快照
- **层级**：Negotiable（触及 INV-01 / INV-03 / INV-13 的部分按不变量守）
- **优先级**：P0

### PRD-M13-002 · 中断当前轮（Web + TUI）

- **用户价值**：发现 agent 跑偏了，可以立刻让它停下，而不是只能等它跑完或关掉程序；停下后已经做的不丢，可以接着说
- **说明**：承接 PRD-M11-007（它只占位、未建任务，等的「终止方案 S1–S4」在仓库里没有记录）。本条直接定语义（疑点 e），拍板后 M11 册标注「由 PRD-M13-002 接手」
- **验收标准**：
  - AC-1: 新 RPC（暂名 `session.interrupt`）：会话忙 → 中止当前轮，回 `{ interrupted: true }`；会话闲 → 回 `{ interrupted: false }` 不产生事件（幂等）
  - AC-2: 模型正在输出 → 流停止，已生成的内容照常落盘并显示
  - AC-3: 工具正在执行 → 收到中止信号（`shell.exec` 结束子进程）；没执行完 / 没开始的工具调用补 `tool.result{ok:false, reason:'interrupted'}`——事件流里没有悬空的 `tool.call`（复用 `recovery.ts` 的一致点规则）
  - AC-4: 这一轮落结束标记（stopReason `interrupted`，事件带是谁中断的：哪个端），轨迹里看得见；`planProgress` 记为被打断，M12-004 AC-10 的「计划还剩 N 步 · 继续」照常出现（突出显示）
  - AC-5: 不自动续跑、不自动重试
  - AC-6: 入口：TUI 运行中按 `Esc` 中断（不退出程序；`Ctrl+C` 语义不变）；Web 运行中发送键旁出现「停止」；中断后输入框可用
  - AC-7: 中断时队列里的补充按 PRD-M13-001 AC-7 退回草稿
- **验收方式**：runtime 单测（流中断 / 工具中断 / 闲时幂等 / 结束标记）+ recovery 一致点回归 + daemon 单测 + TUI 按键测试 + Web SSR 测试
- **层级**：Negotiable
- **优先级**：P1
