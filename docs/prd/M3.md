## 1. 这道门为什么还是要走

`PRD-VISION.md` §7 写着「PROVISIONAL 的里程碑，进入前必须重写为 COMMITTED」。
用户让直接开工，那就把门**压缩**成这一页，而不是跳过：

## 3. 本轮骨架的范围

| PRD | 这一轮做到哪 | 什么时候补齐 |
|---|---|---|
| **M3-001** Domi Protocol | **全做**。它是三端与内核的唯一契约，做一半等于没做 | — |
| **M3-002** daemon | **骨架 + AC-2/AC-4/AC-5 全做**。AC-1 的 `domid` 独立进程与 AC-3 的 kill -9 恢复做到「有测试证明」 | — |
| **M3-004** 并发写仲裁 | **全做**。它是 daemon 设计的直接推论，分开做反而更贵 | — |
| **M3-003** Web 端 | **骨架**：能连上、能看到事件流与轨迹。**AC-1 的 parity e2e 不做**（要 Playwright + 两端各一个用例，是独立一块工作量） | 下一轮；本轮先交付 `docs/parity-checklist.md` 与 AC-2 的依赖守卫 |
| **M3-005** 跨会话引用（P1） | 不做 | 下一轮 |
| **M3-006** 远程连接（P2） | **只做 AC-2 的默认值**：默认只监听 127.0.0.1，且由测试断言 | 认证与 `--connect` 下一轮 |
| **M2-001 / M2-009** MCP | 不做 | 见 `docs/adr/011` 的触发条件 |

**为什么 Web 只做骨架而 protocol 全做**：协议是**共享的契约**，它没做完，后面每个端都要跟着改一次；
Web 端是**一个消费方**，它做一半只影响它自己。在这种不对称面前，优先做完契约是唯一合理的顺序。

## 4. 进入前必须钉死的判据（Invariant 级，不许事后商量）

1. **INV-01 · 协议契约快照**：`packages/protocol/.api.md` 已有；M3-001 AC-3 要求协议类型变更导致 diff 非空则 CI 失败。沿用现有 `guard:api`。
2. **INV-04 · 三端零业务逻辑**：`apps/tui` / `apps/web` 只许依赖 `client-core` / `protocol` / `config`。
   已有 depcruise 规则 `no-logic-in-apps`，M3-002 AC-5 要求把 `memory` 也加进禁止清单。
3. **INV-01 · daemon 是唯一写入者**（M3-004 AC-1）：`client-core` 不许依赖 `store`。加一条 depcruise 规则。
4. **INV-11 · 默认只监听本地**（M3-006 AC-2）：默认配置断言 `127.0.0.1`。
