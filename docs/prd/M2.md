## 5. 门上必须拍板的三件事

### 5.1 MCP SDK 版本（最要紧）—— ✅ 已拍板

> **2026-09-14 结论：选 C，MCP 整体推到 M3。** 用户原话：「MCP 我暂时用不上。可以放到 M3。或者直接用 beta 版本。」
> 两个选项取 C 的判据不是技术优劣，是**需求存在与否**：现在没有要接的 server，
> 为用不上的能力背 beta 的破坏性变更税，是先付钱后确认需求。beta 留作退路。
> 完整理由、影响与「什么时候回来重评」写在 `docs/adr/011`。下面是拍板前的材料，保留不删。

`PRD-M2-001` 明确要求对齐 **2026-07-28** 规范（无状态化，取消 `initialize` 握手与 `Mcp-Session-Id`）。
截至 2026-09-14：

- `@modelcontextprotocol/sdk` 的 **latest 是 1.30.0**（旧的有状态规范）
- 支持 2026-07-28 的是 **v2.0.0-beta**，尚未 GA

| 路 | 换来 | 代价 |
|---|---|---|
| A. 用 v2 beta 并钉死版本 | 规范对齐，M2-001 的 AC 原样成立 | 破坏性变更的人力税。`RECON-DSH` §1 记录过 DSH 钉 rc 的代价：**这是持续成本，不是一次性的** |
| B. 用 v1.30 稳定版 | 不折腾 | `PRD-M2-001` 的 AC-2（MRTR）与 AC-3（列表缓存提示）要**回写降级**——那两条是新规范才有的 |
| C. MCP 整体推到 M3 | M2 专注轨迹与压缩（差异化主体） | M2-009（browser/computer use）跟着推迟，demo 完整度下降 |

**倾向 C**，理由：M2 的价值锚点是轨迹面板与确定性压缩（两个验证过的生态真空），
MCP 是 table stakes 且被上游版本分裂卡住。用一个受制于人的依赖去拖住自己的差异化主体不划算。
但这条必须你拍。
