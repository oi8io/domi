## 1. 本里程碑要回答的问题

**domi 能不能一口气把一个 50 步的任务做完——不崩、不跑偏、不白花钱？**

现状（`docs/RECON-CONTEXT.md` R0，31 个真实会话）：
- **会崩**：一轮中途上下文超出上限就抛异常、不留痕，之后会话再也发不出去（R1）；真实会话的提示词已经到 184k，越过了 150k 的守卫。
- **会跑偏**：开了 `clean` 模型就看不全刚读的文件（R4）；开了 `compact` 长任务压不了（只按用户输入切轮）；记忆层在 DeepSeek 上 6/6 失败、一条都没记下来；内部的 `_memory` 会话泄漏成了用户任务。
- **白花钱**：只追加时缓存几乎完美，但计划一更新就丢 30k token 缓存，验证提示丢 42k；Anthropic 路径根本没发缓存参数；工具结果双层转义多 10–19% token。

M15 把上下文从「拼一份 messages」改成一条**有不变量、有尺子、按厂商渲染**的管线。

## 4. 不做什么

- **不做后台任务小模型路由**（拍板 e）
- **不给用户 `full`**（拍板 c）；它只作为内部参照投影存在
- **不做**（留后续，届时另起条目）：程序性记忆（自动生成 Skill）、后台预压缩、MCP 工具按需加载 / 工具检索、Anthropic programmatic tool calling、OpenAI 服务端加密压缩、推理强度按步切换
- **不改已有事件的语义**：旧会话按旧投影可解析（INV-01）；新形状一律新增事件或新增可选字段
- **服务端能力不是默认路径**（拍板 d）：压缩、遮蔽算法自研是主路径；服务端能力只是可开关的加速

## 5. 需求条目

### PRD-M15-001 · 上下文的尺子：指标、归因与基线命令

- **用户价值**：改上下文策略之后，有数字说明是变好还是变坏；缓存掉了能知道是谁弄掉的
- **验收标准**：
  - AC-1: 每次模型请求记一份**前缀指纹**（工具定义、system、每条历史消息各自的哈希，只记哈希不记内容），随 `model.request` 落盘（可选字段，INV-01）
  - AC-2: 相邻两次请求的前缀第一次不同之处被定位到「哪一层 / 第几条消息 / 由哪个事件引起」；不是压缩点或显式刷新造成的断裂，落一条 `ctx.prefix.break` 事件（INV-12(b) 的运行期观测）
  - AC-3: `session.metrics` 增加：缓存命中率、**可避免的缓存损失**（按 RECON R0 的口径）、本会话压缩 / 遮蔽次数、超窗事故次数；与状态栏、上下文 tab 同源（PRD-M14-006 AC-8）
  - AC-4: `domi doctor --context`：只读扫描本机事件库，输出 RECON R0 那张表（命中率、输入输出比、提示词分布、步数分布、工具结果占比、损失归因、记忆成功率）；不联网、不改库
  - AC-5: L1 fixture 组新增「上下文」一组：前缀稳定性（见 003 AC-6）、压缩保真（压缩前后问同一组关键问题：目标、改过的文件、未决问题，答案来自摘要即可判定）、超窗降级（见 002）
- **验收方式**：runtime 单测（指纹、断裂定位）+ daemon metrics 单测 + doctor 命令对 fixture 库的快照 + L1 回放
- **层级**：Invariant（INV-12、INV-13）
- **优先级**：P0（先做，其余条目用它验收）

### PRD-M15-002 · 超窗不崩：模型窗口、预算器与降级链

- **用户价值**：任务做得再长也不会突然卡死；真到极限时 domi 说清楚发生了什么、给出能点的出路
- **验收标准**：
  - AC-1: 模型目录带 `contextWindow` 与 `maxOutput`（内置常用模型；未知模型可在设置里填，填不了按保守默认值并提示）；`context.maxTokens` 不再是全局常数，改为按当前模型算**有效窗口** = 窗口 − 输出预留 − 安全余量（建议 i）
  - AC-2: **预算器**统一口径：以最近一次真实 usage 为基准 + 新增内容的增量估算（含 system、工具定义、输出预留）；守卫、阈值、状态栏、上下文 tab 全部读它（RECON C3）
  - AC-3: 每一步请求前做预检，超阈值时按**降级链**逐级处理，每一级落事件：遮蔽一批冷区（004）→ 压缩（005，可在**轮中**执行）→ 仍超则本轮停下并落 `error{scope:'context', recoverable:true}`，附可执行的出路（压缩更多 / 开新会话并带上摘要 / 换更大窗口的模型）
  - AC-4: **任何**拼装阶段的异常都转成事件落盘，不穿出 `runTurn`；会话不会进入「每次 submit 都失败」的状态——R1 的复现用例改为断言：第二次 submit 能正常跑（必要时先自动压缩）
  - AC-5: 切换到更小窗口的模型时，切换前预检；放不下就先压缩再切，并在 `model.switch` 旁落一条说明
  - AC-6: 压缩连续失败 N 次熔断（不再每轮重试），状态栏与上下文 tab 提示，手动压缩仍可用（RECON S6）
- **验收方式**：kernel / runtime 单测（预算器口径、降级链每一级、轮中压缩、异常转事件）+ R1 复现用例转绿 + 模型切换单测 + L1「超窗降级」fixture
- **层级**：Invariant（INV-01、INV-12）
- **优先级**：P0

### PRD-M15-003 · 前缀只增不改：动态内容改追加、会话级冻结

- **用户价值**：同样的任务少花钱、更快；改了 Soul 或规矩不会悄悄让当前会话的缓存全部作废
- **说明**：INV-12(b) 的落地（ADR-029）
- **验收标准**：
  - AC-1: 会话开始时（以及压缩点、显式刷新时）定格一份**前缀快照**：工具表、内置层、项目规矩、Soul、记忆索引、技能清单；会话内这些来源的变化不进当前请求
  - AC-2: 计划、环境变化、验证提示、运行中补充以**追加事件**送达（暂名 `ctx.note`），渲染为新的 user 块；不再修改任何已发出的消息；计划只在内容变化时追加一次
  - AC-3: 冻结期间来源有变化时，上下文 tab 与状态栏显示「N 项更新将在新会话生效 · 现在刷新」；刷新按钮不做预检弹窗，直接触发一次显式刷新并落 `ctx.refresh` 事件（INV-12(b) 白名单内），之后的请求用新快照
  - AC-4: Soul / 记忆的后台更新照常写盘，只是不进当前会话（ADR-019 已回写）；新会话立刻用上
  - AC-5: 工具表在会话内稳定：工具定义顺序、描述、schema 序列化逐字节一致（键排序）；需要限制工具时用 `tool_choice` / 允许列表，不删定义
  - AC-6: **前缀稳定性回放（CI 门禁）**：L1 fixture 覆盖计划更新、`verify.required`、运行中补充、新一轮、Soul 改动、同一文件读两次、信任仓库；断言相邻请求「前者是后者的前缀」，压缩点与显式刷新除外
  - AC-7: 用 R0 同口径复测：除压缩点与显式刷新外，相邻请求的平均缓存损失 ≤ 64 token（DeepSeek 的缓存粒度内）
- **验收方式**：prompt / runtime 单测（快照定格、追加渲染、刷新）+ 前缀稳定性回放（CI）+ doctor 复测数字写回 RECON
- **层级**：Invariant（INV-12）
- **优先级**：P0

### PRD-M15-004 · 遮蔽与清理：冷区一次决定、热区不动

- **用户价值**：旧的、用过的工具输出自动收起，窗口留给正在做的事；刚读的文件永远看得全
- **说明**：取代现有 `clean` 策略；属于「均衡 / 节省」两档的第一道（建议 g）
- **验收标准**：
  - AC-1: **热区**（最近 K 步，且至少最近 T token 的工具输出）原样；只有**冷区**可以被遮蔽或清理（R4 的复现用例改为断言：刚读的 300 行文件模型能看到第 150 行）
  - AC-2: 遮蔽 = 冷区工具结果换成一行指针（工具名、参数摘要、原始大小、「需要时重读」）；工具调用本身与错误信息保留（Manus「保留错误」）
  - AC-3: **决定落事件**（暂名 `ctx.mask`，带被遮蔽的 seq 列表与原因）；按批做，在阈值触发或压缩点一次决定一批，单批至少腾出 X token（同 Anthropic `clear_at_least` 的道理）；已遮蔽的不再变（INV-12(a)(b)）
  - AC-4: 原有确定性规则（去重、已解决错误、堆栈截断、冗长输出）改为只作用于冷区、随遮蔽批次一起决定；不再回溯改写热区或已发出的部分
  - AC-5: 用户可以**钉住**某条事件（不遮蔽、不清理、压缩时原文保留）；本期交互只做 `/pin <seq>` 命令 + 上下文 tab 每条遮蔽记录旁的 📌 按钮，不做 TUI 快捷键与批量钉住；钉/解钉均落 `ctx.pin` 事件
  - AC-6: 冷区里被遮蔽的内容在上下文 tab 可见（哪一步、原始大小、可定位）
- **验收方式**：memory 单测（热区 / 冷区划分、批次、钉住、规则只动冷区）+ R4 用例转绿 + 前缀稳定性回放 + L2 题集对比「遮蔽 vs 不遮蔽」完成率不降
- **层级**：Invariant（INV-12）
- **优先级**：P0

### PRD-M15-005 · LLM 压缩 v2：按步、增量、可轮中、保真

- **用户价值**：压缩之后 domi 还记得要干什么、改过什么、卡在哪；长任务也压得动
- **验收标准**：
  - AC-1: 压缩边界按**步**（模型请求）切，保留最近 K 步 + 最近 T token；单轮长任务也能压（Q2）
  - AC-2: **增量**：输入 = 上一份摘要 + 上次压缩点之后的对话事件；不再从第 1 条事件重摘（S2）；摘要不会被再次当成原文摘要
  - AC-3: 摘要输入只含进上下文的那几类事件（用户输入、补充、正文、工具调用、已遮蔽的指针或未遮蔽的结果、计划、验证提示）；轨迹事件（usage、request、permission、快照）不进（S3）
  - AC-4: 摘要模板扩到：目标与约束、**用户说过的每句话（原文）**、关键决定、改过的文件与要点、错误与修法、当前正在做的那一步的精确状态、未决问题、下一步；仍是固定字段、zod 校验
  - AC-5: 压缩后**补水**：重新附上最近读 / 改过的 K 个文件的路径与需要时重读的提示，已 `skill.load` 的技能正文，当前计划；编辑守卫（stamps）对被压缩掉内容的文件失效，改之前必须重读（Q4）

### PRD-M15-006 · 厂商适配层：缓存参数、工具结果、推理块、服务端能力开关

- **用户价值**：用哪家模型都按那家的规矩省钱；Anthropic 不再零缓存

- **验收标准**：

  - AC-2: OpenAI 系（OpenAI、兼容网关）：发 `prompt_cache_key`（会话 id），支持时可配保留时长；DeepSeek / Z.ai 等自动缓存厂商不需要参数，但能力表 `promptCache` 改为与实际一致（DeepSeek 现在误标 false）
  - AC-3: 工具结果以**纯文本**发出（边界标记在文本里，结构化字段渲染成一行文本头 + 原文），去掉双层转义；用 R3 的方法复测，工具结果 token 回到原文 +3% 以内
  - AC-4: 推理块按厂商协议处理：需要回传的（Anthropic 交错思考、Z.ai preserved thinking）在**本轮内**原样回传（含签名）；跨轮按厂商规则丢弃或保留；不需要的（DeepSeek v4，R0 已验证）不传；不再把推理拼进正文
  - AC-5: 服务端能力（Anthropic compaction、clear_tool_uses）接入，**默认关**，按会话 / 全局开关打开（拍板 d）；打开时每次服务端改动视为一个压缩点，服务端返回的 `applied_edits` / 压缩块落事件（INV-12(a) 可追溯）；关掉时行为与自研路径一致
  - AC-6: 能力探测与降级：厂商不支持某项时不发、不报错，并在 `domi doctor` 里列出「这家支持什么、开了什么」
- **验收方式**：model 单测（各厂商请求体快照：缓存参数、工具结果文本、推理块）+ R3 复测 + 服务端能力开关的请求体对比 + stub provider 回放

- **优先级**：P0（AC-5 为 P1）

### PRD-M15-008 · 记忆可靠：内部会话隔离、结构化输出降级
