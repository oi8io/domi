## 2. 取舍记录

### SPEC-M13-001 · 运行中补充

**取舍-1 · 队列放在 daemon core，runtime / kernel 只拿一个「取」端口**
- 候选：①端上排队（到下一轮再发）②runtime 的 DomiSession 里排队 ③daemon core 里排队。
- 选 ③。「会话忙不忙」的唯一裁判是 core（`this.busy` 在 `session.submit` 里同步占位，`core.ts` 文件头的硬规则 2）。队列要跟这个判断**原子**地一起做，否则有两个窗口会丢补充：
  - core 已接受提交、还在 `await checkReady / checkRefs`，runtime 还没开始跑——放 runtime 的话它会说「我闲着」
  - runtime 已经收场、core 的 `.finally` 还没把 busy 删掉——补充进了队列，却没人再取
- ① 被否：多端看不到同一份队列（AC-5），而且「下一步送达」做不到。
- 做法：core 为每个**由 core 发起的**一轮（`session.submit` / `session.note` 转提交）建一个 `ActiveTurn { queue: Note[], ac: AbortController }`，放在 `Map<sessionId, ActiveTurn>`。`SessionHandle.submit` 多一个可选参数 `run?: { notes: NoteSource; signal: AbortSignal }` 传下去。host 自己发起、不经过 core 的轮（评审会话：`runtime-host.ts` 直接 `s.submit`；定时任务与长任务节点：`task-service.ts` 直接 `s.submit`）没有 ActiveTurn——这时 `session.note` 回 `SESSION_BUSY`，不排队。

**取舍-2 · 送达点在 kernel 的两个安全点，经端口取，kernel 仍然零 IO**
- `LoopDeps.notes?: NoteSource`，`interface NoteSource { take(): ReadonlyArray<{ id: string; text: string; from?: string }> }`——取走即清空，调用方负责广播队列变化。
- 安全点 ①：`for (;;)` 每一步开头，墙钟 / 中断检查之后、`sink.read` 之前。此时上一步的 `tool.result` 都已落盘（loop 是逐个 `await` 追加的），不会插进 tool_use / tool_result 之间。
- 安全点 ②：本步没有工具调用、`beforeComplete` 没要求再来之后、`return completed` 之前。取到了就追加并 `continue`（AC-3）；这一步照常经过墙钟检查，工具调用计数器照常累加。
- 取到的每条补充各落一条 `user.note`，同一批 append（保持发送顺序，seq 连续）。
- 不在别处送达：模型流进行中、工具执行中、等确认时都不送达（AC-8），等工具返回后的下一个安全点 ①。
- 先例：`verify.required` 就是在模型收场时由运行时追加、进上下文变成一条 user 消息（`build-context.ts`），provider 适配层已经处理过「tool 结果后跟 user 消息」。

**取舍-3 · 新事件 `user.note`，不复用 `user.input`**
- schema：`{ t: 'user.note', id: string, text: string, from?: string }`。`id` 是 core 分配的 noteId（端上凭它把「排队中」对上「已送达」）；`from` 是发送端的名字（`domi-web` / `domi-tui`，握手时报的），轨迹里看得见。
- `user.input` 是轮边界，复用会破坏分页（M11-009）、引用本轮、分支、标题、verify 的「这一轮」判定、memory 的轮数统计。
- `buildContext`：`case 'user.note'` → `flush()`，连续的补充**合并**成一条 user 消息，前缀 `[运行中补充]`（和 `[运行时提示]` 同一风格，中文，模型侧不做 i18n）。
- 影响清单（全仓 `'user.input'` 的 25 处逐一过；★ = 要改）：

| 位置 | 处理 |
|---|---|
| ★ `kernel/build-context.ts` | 见上 |
| ★ `kernel/paginate.ts` `weightLines` | 按 `user.input` 同样计行；`splitIntoTurns` **不**切（AC-4） |
| ★ `kernel/refs.ts` | 跨会话引用渲染：补充按用户文字带「补充」标注 |
| ★ `memory/strategy.ts`（压缩摘要取文本） | 与 `user.input` 同列 |
| ★ `memory/cleanup.ts` `projectText` | 与 `user.input` 同样返回 text |
| ★ `memory/semantic.ts`（记忆抽取） | `[seq] 用户（补充）：…` |
| ★ `store/search.ts` | `INDEXED_TYPES` 加 `user.note`，能搜到 |
| ★ `trace/model.ts` | 轨迹节点：用户补充 |
| ★ `client-core/store.ts` | 投影成 `{ kind: 'user', note: true, noteId, text }` |
| ★ `eval/fixture.ts` / `replay.ts` | 见取舍-7 |
| `kernel/recovery.ts` · `verify.ts` · `metrics.ts` · `usage.ts` | 不改：补充不开新轮、不改 open 状态 |
| `memory/compact.ts` 的轮起点 · `runtime/memory-service.ts` 轮数 | 不改（不是新轮） |
| `runtime/session.ts` `changedThisTurn` / 标题 `firstInput` / `lastAnswer` | 不改（`lastAnswer` 按 `model.request` 重置，补充后的那次请求自然重置） |
| `runtime/plan.ts` `onUserInput` / interrupted 复位 | 不改——补充不触发「阻止提示」审批（见 §3 留白 1），也不复位 interrupted（补充发生在一轮之内） |
| `store/sessions.ts` `message_count` / `first_input` · `read-marks.ts` `last_input` · `projects.ts` | 不改 |

**取舍-4 · 收场时的残留：正常收场转新一轮，异常收场退回**
- 残留只可能来自竞态：kernel 在安全点 ② 取空、决定收场之后，到 core 的收尾之间又来了补充。
- core 收尾（原来的 `.finally(() => this.busy.delete(id))`）改成同步判定：
  - `stopReason === 'completed'` 且队列非空 → **不释放 busy**，立即用残留开下一轮：`user.input.text` = 残留按发送顺序用空行拼起来，`user.input.noteIds` = 这些补充的 id（实现时补的可选字段：端上凭它认作「已送达」，否则重连对账会把它们当成退回、在草稿里重复出现）。对用户等价于「会话闲时发送」（`session.note` 闲时本来就是提交），不产生第二套语义。
  - 其他 stopReason（`stream_error` / 护栏 / `budget` / `interrupted`）或 `submit` 抛错 → 清空队列，广播 `session.notes.returned { sessionId, notes }`，再释放 busy。
- 判定与释放 busy 之间没有 `await`（与 `session.submit` 里「检查与占位之间不许有 await」同一条纪律）。
- `SessionHandle.submit` 的返回值约定为 `{ stopReason?: string }`（runtime 的 `TurnResult` 本来就是），老宿主返回别的 → 当作 completed。

**取舍-5 · RPC 与通知**

| 名称 | 形状 | 说明 |
|---|---|---|
| `session.note` | params `{ sessionId, text: string.min(1).max(200_000) }` → `{ state: 'queued', noteId } \| { state: 'submitted' }` | 有 ActiveTurn → 入队；完全空闲 → 走与 `session.submit` 同一个 `startTurn`（同样校验凭据）；只有 host 忙 → `SESSION_BUSY` |
| `session.note.withdraw` | `{ sessionId, noteId }` → `{ withdrawn: boolean }` | 在队列里 → 删掉、广播；不在（已送达 / 已退回 / 不存在）→ `false`，不产生事件（AC-6） |
| 通知 `session.notes` | `{ sessionId, pending: Array<{ id, text, from? }> }` | 队列每次变化推一次；订阅时补发一次（和 `session.busy` 一样） |
| 通知 `session.notes.returned` | `{ sessionId, notes: Array<{ id, text, from? }> }` | 异常收场退回（AC-7） |

- noteId：`n-<时间戳>-<随机>`，只在 daemon 进程内唯一即可（重启后队列本来就没了）。
- 「谁发的」用握手时的 `clientName`（`this.clientNames`），不用 conn.id——同一个端重连后 conn.id 会变。

**取舍-6 · 端上：本地副本 + 草稿恢复**
- client-core：`note(sessionId, text)`、`withdrawNote(sessionId, noteId)`；store 新 atom `$notes`（daemon 推的队列）与 `$returned`（等待恢复进草稿的文本，端上取走后清空）。
- 本地副本：client-core 记下自己发出的 `noteId → text`，直到看到同 id 的 `user.note`（已送达）、`session.notes.returned`（退回）、或撤回成功。重连并重新订阅后，收到 `session.notes` 快照时，本地副本里既不在快照、也没看到送达事件的，按「退回」处理——覆盖 daemon 重启丢队列的情况（AC-7 后半）。
- 退回只恢复进**发送它的那个端**的草稿（凭本地副本认领）；其他端只是排队条消失。
- 草稿恢复：`$returned` 里的文本拼到输入框现有内容之前，空行分隔；不覆盖用户正在打的字。
- Web Composer：`busy` 时不再禁用输入与发送；发送走 `note`（闲时走原来的 `submit`，附件 / 文件 / 技能照旧可带）。`busy` 时附件、文件、技能按钮禁用（首版补充只收文本，PRD §2 d）。输入框上方排队条：「排队中 · 下一步送达（N）」，每条可撤回。
- Transcript：`note: true` 的用户气泡带「补充」小标签，不显示「引用本轮 / 分支」这类按轮操作。
- TUI：`<Prompt disabled={busy}>` 去掉禁用；回车时 busy → `note`，否则 `submit`；输入框上方一行排队提示（条数 + 最新一条摘要），撤回用 `/unqueue`（撤回最后一条）。

**取舍-7 · 评估回放（INV-13）：补充按「第几次模型请求之前」录制**
- `Fixture` 加可选 `notes?: Array<{ beforeRequest: number; text: string }>`，`beforeRequest` = 这条补充之前出现过几次 `model.request`（从 0 数）。`version` 仍是 1（可选字段，旧 fixture 照读）。
- `replay.ts` 给 `runTurn` 一个 `NoteSource`：按已发出的请求次数返回该送达的补充。回放出来的事件流里补充落在同一步（AC-10）。

**反悔成本**：低。事件是新增的，删掉功能后旧会话里的 `user.note` 仍可解析、照常进上下文；RPC 与通知都是新增。

### SPEC-M13-002 · 中断当前轮

**取舍-1 · 中断信号走 ActiveTurn 的 AbortController**
- RPC `session.interrupt { sessionId }` → `{ interrupted: boolean }`：有 ActiveTurn → `ac.abort({ by: clientName })`，回 `true`；没有 → `false`，不产生事件（幂等，AC-1）。
- 信号链：core `ActiveTurn.ac.signal` → `SessionHandle.submit(…, { signal })` → `DomiSession.submit(opts.signal)` → `runTurn(deps, id, input, signal)`（`runTurn` 已经接受外部 signal，只是 runtime 从没传过）。
- `by` 放在 `signal.reason` 里，kernel 读出来写进结束事件，不为它加参数。

**取舍-2 · kernel 的中断语义**
- `StopReason` 加 `'interrupted'`。区分「外部中断」和 loop 自己 `stop()` 时的 `ac.abort()`：只看外部 `signal?.aborted`。
- 检查点：①每一步开头（与墙钟检查并列，先于补充送达）；②模型流结束后（不管 provider 是抛错、报 error 事件、还是正常结束）；③每个工具返回后。
- 流中断：`produced`（已吐出的 delta / reason / 已解析的 tool.call）**照常落盘**（AC-2，现有代码在 streamError 路径已经这么做）；本步已解析出的工具调用一个都不执行。
- 工具中断：正在跑的那个工具返回的结果照录，`reason` 改成 `'interrupted'`；排在它后面的调用补 `interruptedResult(id)`（`ok:false, reason:'interrupted'`，文案「本轮被用户中断，没有执行」）——与 `notRunResult` 并列，不复用，因为 PRD AC-3 要的是 interrupted。
- 结束事件：沿用 `stop()`，`error { scope: 'loop', message, recoverable: true, counters, stopReason: 'interrupted', by }`。`scope: 'loop'` 让 `recovery.turnState` 把这一轮看成已结束；`planProgress` 看到 `error` 事件 → interrupted = true，M12 的「计划还剩 N 步 · 继续」照常突出显示（AC-4）。
- `error` schema 加两个**可选**字段 `stopReason?: string`、`by?: string`；顺手让所有 `stop()` 都写 `stopReason`（轨迹排查受益，旧事件没有照样解析）。

**取舍-3 · 等确认 / 问题框时被中断**
- core 在 `abort` 之后，把这个会话所有挂着的 ask 以 `answer(false, undefined, 'interrupt')` 结掉并广播 `session.askDone`。权限事件的 `channel` 是 `interrupt`，审计上看得出不是用户点了拒绝。工具拿到拒绝后返回，kernel 在检查点 ③ 把它的结果改成 interrupted。
- 问题框（`ask.user`）同理，工具结果如实说「用户中断了这一轮，没有回答」。

**取舍-4 · 长时间工具与子 agent 要真的停**
- `shell.exec` 已监听 `ctx.signal` 结束子进程，不改。后台 job（`shell-jobs`）是用户 / 模型显式放到后台的，不随中断结束（§3 留白 2）。
- `spawn`（子 agent）现在不看 signal：父轮中断后仍要等子 agent 跑完才返回，中断形同虚设。改为把 `ctx.signal` 传给子会话的 `submit`，子 agent 以 interrupted 收场，父轮的 spawn 结果如实说「子 agent 被中断」。
- 其他工具不看 signal 的，检查点 ③ 会在它返回后停下——最坏情况是等这一个工具跑完，不会再开新的。

**取舍-5 · 两端入口**
- Web：`busy` 时发送键旁出现「停止」按钮（`data-action="interrupt"`）；不设快捷键（`Esc` 在浏览器里被弹层、下拉占用太多）。
- TUI：`routeKey` 之前加一条纯函数判定 `isInterruptKey(key, { busy, overlay, ask })`：`Esc` 且 busy 且没有弹层、没有待答的询问 → 中断。有弹层 / 询问时 `Esc` 仍归它们（问题框里 `Esc` = 不回答）。`Ctrl+C` 语义不变。草稿不清空。
- 中断后：busy 通知翻回 false，输入框回到闲时行为；队列里的补充按 SPEC-M13-001 取舍-4 退回草稿（AC-7）。

**反悔成本**：低。RPC 新增；kernel 的检查点只在外部 signal 触发时生效，不传 signal 的调用方（回放、单测）行为不变。

## 3. 明确留白

1. **补充不参与「阻止提示」审批判定**（`plan.onUserInput`）：中途想叫停用中断；补充里写「先别动」不会让计划重新进入待批。以后要做，在安全点送达时把文本交给 plan 即可。
2. **后台 job 不随中断结束**：它们本来就脱离了这一轮。
3. **补充不带附件 / 引用 / 技能**（PRD §2 d）。
4. **定时任务 / 评审会话等 host 自己发起的轮不接受补充、也不能从这里中断**（没有 ActiveTurn）：它们各有自己的入口（`task.cancel`）。
