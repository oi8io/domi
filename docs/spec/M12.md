## 2. 取舍记录

### SPEC-M12-003 · 改名同步已工作，只清理空标题死分支

- **实测**（2026-09-23 bu 浏览器）：点标题改名 → Enter → 右上角立即更新新名；回首页侧边栏也同步。PRD 说的「改名后右上角不更新」在当前代码已不复现——M10-001 修 titleOf 时一并修好了刷新链路（onRenamed → refreshSoon → listSessions → setSessions → activeRow?.title 更新）。
- **剩余问题**：SessionTitle 里 `title === '' ? tr('common.untitled') : title`。但 daemon `listSessions` 已做空标题回退（`r.title.trim() !== '' ? r.title : r.firstInput ?? untitled`），前端拿到的 `title` 永远非空——这个三元分支是死代码。
- **选**：删死分支，直接 `{title}`（title prop 可能 undefined 时兜底空字符串）。空标题口径以 daemon 返回的 firstInput 为准（与侧边栏同源），前端不再自己判"未命名"。
- **反悔成本**：极低。

### SPEC-M12-001 · model.resolve RPC 直接删，不留兼容

- **现状**：Web ModelSwitch 有「搜索 / 手填…」→ custom 模式 → `client.resolveModel(text)` → `model.resolve` RPC（按名字归属 provider）。TUI `/model <名字>` 走 daemon 直接接收模型名。
- **选**：Web 删 custom 分支（`<input> + datalist` 整段删），只留 `<select>`；TUI `/model <名字>` 手填路径删（只开选择器）；`model.resolve` RPC 定义 + 实现 + 测试全删。
- **理由**：PRD 定案 a「两端都不要手填」；`model.resolve` 无调用方后留着是死代码。
- **反悔成本**：低。将来要加回手填就重新加 RPC。
- **清单为空时**：select disabled + CredentialNotice 引导去设置页（AC-4）。

### SPEC-M12-002 · permissions.mode 会话级，mode 字段复用

- **现状**：M11-005 实现为全局 `permissions.review`（config schema + 白名单），Web 设置页 RuntimeTab 三档下拉，TUI SettingsOverlay 三档，runtime `session.ts` `reviewMode: () => opts.config.permissions.review`。
- **改为**：
  - config 删 `permissions.review` 全局项
  - runtime session 维护会话级 `permissionsMode`（默认 `on-demand` 写代码常量），新事件 `permissions.mode.switch`（值 `always-ask | on-demand | allow-all`）
  - 写事件流（INV-01），重开会话从事件流恢复
  - Web Composer 工具栏加三档小下拉（照图 1：标题 + 描述列表式）
  - TUI `/mode` 斜杠命令 + 补全
  - Web 设置页 RuntimeTab 删三档；TUI SettingsOverlay 删三档
  - 全仓 `review` 残留清：i18n key `web.settings.review*`、`reviewMode` 变量名、TUI 命令、文档
- **档位语义**（2026-09-23 用户拍板后改写，PRD v1.14；原文「危险能力任何档都确认」作废）：
  - `always-ask`：危险能力即使规则 allow 也问；无规则的非危险能力也问
  - `on-demand`（默认）：用户写的规则算数；没写规则的危险能力拒
  - `allow-all`：跳过所有确认（同 Claude 的 skip all approvals），只剩显式 deny 与父范围；放行记 `source: mode`
- **与 M12-004 关系**：计划审批跟档位走，见 SPEC-M12-004 第二轮。
- **状态栏**（第二轮，PRD-M12-002 AC-9）：metrics 已经带 `permissionsMode`；Web StatusBar / TUI StatusBar 显示档位名，`allow-all` 用 danger 色。不新增协议字段。
- **命名收尾**（第二轮）：`@domi/capability` 的 `ReviewMode` / `reviewMode` 改名 `PermissionsMode` / `permissionsMode`，不留别名（AC-8）。
- **反悔成本**：中。改名面广，但都是机械替换。

### SPEC-M12-004 · plan/act 删除，确认弹框取代 elicit 表单

- **现状**：plan/act 两模式。plan 权限分支只放行只读 + `plan.submit`；`plan.submit` 走 `ctx.elicit` 表单审批。
- **改为（B 方案）**：
  - 删：权限引擎 plan 分支（`PLAN_MODE_READONLY`、`PLAN_SUBMIT_CAPABILITY`）、session mode/setMode/AUTO_PLAN_REASON、Composer ModeToggle、`mode.switch` 事件语义
  - 新流程：系统直接产出计划 → 需要确认的点整理成弹框（每题一个 tab，abcd 选项 + 自定义输入）→ 确认后执行
  - 无确认点 + 无阻止提示 → 直接执行
  - 阻止提示判定：关键词（不要/别/禁止/先别）+ 对象，有则停下来先问
  - 转长任务能力保留（plan.submit 的 asTask 语义平移）
- **确认弹框形态**：Web 端复用现有 ask/dialog 组件，多 tab 按问题数分；TUI 端逐步展开。
- **反悔成本**：高。动权限引擎 + runtime 核心循环。

### SPEC-M12-004 第二轮 · 问题框 + 计划必须 + 审批跟档位 + 一键续跑

> 触发：用户 2026-09-23 第二轮拍板（PRD-M12-004 AC-7…AC-10）。第一轮「确认弹框取代 elicit 表单」的口径由本节取代。

**取舍-1 · 问题框走现有询问通道，不加协议字段**
- 形态照 Claude Code 的 AskUserQuestion：`ask.user` 工具，参数 `{ questions: [{ header ≤12 字, question, options: 2–4 × { label, description }, multiSelect? }] }`，1–4 题；「其他」自定义输入不用模型声明，永远有。
- 传输：复用 `session.ask` 的 `form`。`form.schema` 同时带两样东西：扩展键 `x-domi-questions`（问题原样）+ 一份普通 JSON Schema（每题一个 enum 字段 `q1…q4`，外加 `q1_other…` 字符串）。认识扩展键的端（Web、TUI）画多 tab；不认识的（旧客户端、Telegram 桥接）按普通表单画——不改协议、不升协议版本。
- 回答：新端回 `content = { answers: [{ selected: string[], other?: string }] }`（按题序）；降级表单回 `{ q1, q1_other, … }`。runtime 的 `normalizeAnswers` 两种都认，交给模型的一律是 `[{ header, question, answer }]`。
- 没人能回答 → decline，工具结果如实说「用户没有回答」，不替人选（与 TASK-M3-016 同立场）。
- 契约（zod schema、`questionsToForm`、`normalizeAnswers`）放 `@domi/protocol`：runtime 和两端都要用同一份，放 client-core 的话 runtime 用不到。
- 为什么不新建事件：问题在 `tool.call` 的参数里、答案在 `tool.result` 里，事件流已经完整；对话流里把 `ask.user` 的调用 / 结果渲染成问答卡片即可。

**取舍-2 · 计划是一个工具 + 一条新事件（SCHEMA_VERSION 14）**
- `plan.update`：参数 `{ steps: [{ id, text, status: pending | in_progress | done | skipped, dependsOn? }], note? }`，**整份替换**（同 Claude Code 的 TodoWrite）——比增量 patch 简单，投影只看最后一条。
- 事件 `plan.update { steps, note? }`：只增不改，投影 = 最后一条。`plan.proposed` 不再产生（类型保留读旧会话）；审批沿用 `plan.decided`。
- **常驻上下文**：runtime 每轮从内存里的计划状态拼一个动态提示词层 `session.plan`（role user、不缓存），压缩时它不在被压的消息里，所以不会丢。重开会话从事件流最后一条 `plan.update` / `plan.decided` 恢复。
- 能力：`ask.user`、`plan.update` 是「和用户说话」，不碰外部世界——runtime 以 extraRules 内置 allow（排在用户规则前面），不进危险清单；用户想禁也可以写 deny（allow-all 下 deny 仍生效）。

**取舍-3 · 「计划必须」与审批用 ToolRegistry 的闸门做，不进权限引擎**
- 闸门（`gate`）在权限之前执行，已有预算闸门；扩成可组合、并加一种结果 `reject`：这次调用不执行、工具结果带原因、**这一轮不结束**（预算闸门的 `stop` 会结束一轮）。reason 分别是 `plan_required` / `plan_unapproved`，不落 `permission` 事件——这不是权限决定。
- 放行集合（只读 + 和用户说话）：`fs.read`、`code.*`、`memory.search`、`memory.recall`、`skill.load`、`ask.user`、`plan.update`、`review.report`。其余一律要先有计划。
- 只对**任务会话**的顶层会话强制（runtime 选项 `planRequired`，daemon 按 `kind === 'task'` 且不是子 agent / 长任务节点时给）；子 agent 和 DAG 节点本身就是计划里的一步，不再要求。自由会话不强制，模型觉得复杂可以自己写。
- **审批**：需要审批时，`plan.update` 第一次写出计划（或上一次被驳回后再写）就在工具里弹审批问题框（单题：批准执行 / 批准并转成长任务 / 其他 = 修改意见），结果落 `plan.decided { approved, comment?, asTask?, runId?, shape, source: 'user' }`。需要审批 = `always-ask`，或本轮用户输入命中阻止提示；`allow-all` 永不审批；`on-demand` 且无阻止提示 → 不审批。没批准前闸门拒绝非放行集合的工具。
- **阻止提示**：纯函数 `blockingHint(text)`，中英关键词正则（先别 / 别急着 / 不要直接 / 先给方案 / 先出计划 / 等我确认 / 确认后再 / 只要计划 / don't start / wait for my approval / plan only …），命中返回命中的片段；判定按「最近一条用户输入」。宁可多问：误判的代价只是多点一次批准。
- 转长任务：审批选「批准并转成长任务」时，沿用 `stepsToDag` + `startTask`；步骤少于 3 或没有可并行时照样在本会话执行，并如实告诉模型。

**取舍-4 · 续跑是端上的一个按钮，不是 daemon 自动续跑**
- client-core 投影 `planProgress = { steps, done, total, remaining, interrupted }`：`interrupted` = 最后一轮以中断收场（`tool.result.reason ∈ { interrupted, not_run }`、`error` 事件、或 recover 补过一致点）。
- Web：会话页 Composer 上方一条「计划还剩 N 步 · 继续」（interrupted 时用警示色）；TUI：输入框上方一行提示，`/continue` 命令。两者都只是提交一条固定的用户输入「继续执行计划里没做完的步骤」（i18n），计划本身已经在上下文里。
- 不做自动续跑：用户拍板「提示后一键续跑」。

**取舍-5 · 项目设置里的「计划审阅策略」从界面移除**
- PRD-M8-005 AC-3 在 v1.14 已划掉，审批改由确认模式决定。Web 项目页的下拉删掉，runtime 不再读；存储与协议里的 `planReview` 字段保留（旧数据照读），注释标明已废弃。

**反悔成本**：中。闸门、工具、事件都是新增，删掉即回到「无计划」；唯一的事件新增走 SCHEMA_VERSION 14。
