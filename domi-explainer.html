01 · 运行时架构（as built）

单进程装下全部业务，三端零逻辑

domid（daemon）持有全部业务逻辑；TUI / Web / Desktop 只做渲染，通过 Domi Protocol 走 WebSocket（JSON-RPC 2.0 子集，PROTOCOL_VERSION=1，方法 / 通知分离，版本不匹配直接断开，不降级）。加一个端 = 纯前端工作（INV-04）。

TUI Web Desktop
Domi Protocol · WebSocket · session.submit / session.events / session.ask
domid — packages/daemon · runtime-host.ts 装配

kernel packages/kernel · loop.ts · build-context.ts

纯函数，零 IO（dependency-cruiser 的 no-io-in-kernel 守）。runTurn 只认注入的 sink / provider / tools / clock；事件怎么拼成上下文由 buildContext 决定。

runtime packages/runtime · session.ts

DomiSession 装配点：把 kernel + store + capability + memory 拧成一个会话。submit / askApproval / recover / compactNow / spawn 都在这里接线。

store packages/store · SqliteEventLog

append-only 事件日志 + 会话表（title / cwd / kind / lastMessageAt）+ 分支视图（视图 seq = 自身 seq + offset）。事件只增不改。

capability packages/capability · PermissionEngine · ToolRegistry

工具注册 + 权限引擎。默认拒绝（INV-03）；权限决策全部落成 permission 事件，事后可审计。

orchestrator packages/orchestrator · runner.ts · spec.ts

DAG 任务编排。运行状态 = 对事件流的纯投影，不落状态文件；重启靠重放回到原处。

memory + checkpoint packages/memory · packages/checkpoint

上下文压缩 / L3 抽取 / Soul；ShadowRepo 影子仓库做步级快照（SPEC-M14-003）。

事件信封

{ seq, sessionId, parentSeq, ts, schemaVersion: 17, ev }

51 种事件类型，SCHEMA_VERSION 从 v1 逐版递增到 17。未知类型降级为 UnknownEvent 保留原文——INV-01「永远可解析」的实现方式。

上下文边界：只有 4 类事件喂给模型

user.input / model.delta / tool.call / tool.result 进 messages；model.reason / model.request / model.usage / permission / error 是轨迹事件——要被看见、被审计，但不喂给模型，否则上下文被自己的元数据撑爆。

工具结果用私有区字符 \uE000…\uE001 包边界——压缩、摊平之后区分仍在，内容里出现这两个字符会被剥掉（防伪造边界注入）。

51 种事件类型（高亮 = 进模型上下文）

user.input user.note ctx.note ctx.ref ctx.fileref model.delta tool.call tool.result verify.required model.request model.reason model.usage model.switch permission permissions.mode.switch error ctx.cleanup ctx.compact ctx.mask ctx.pin ctx.refresh ctx.prefix.break memory.write snapshot revert workspace.trust hook.run mode.switch fs.snapshot fs.checkpoint fs.discard task.run task.node task.spawn task.resume task.retry task.end plan.update plan.proposed plan.decided worktree.create worktree.discard worktree.restore worktree.apply project.assign schedule.fire session.kind budget.warn budget.decided plugin.error review.findings

事件类型是协议的一部分——只增不改，改了就是新版本（v1→v17 每一步变更都留在 event.ts 的注释里）。

02 · 会话生命周期与时序

一轮对话，从 submit 到 completed 发生了什么

会话是一段 append-only 事件流 + 一个 SQLite 会话行。daemon 重启、被 kill -9、换客户端都不丢状态——因为真相只在事件里。

生命周期状态

createdchat → scratch 目录 createdtask → 项目目录 / git worktree idle ⇄ busy一轮 loop 运行时 busy=true soft-delete事件保留 · 可 restore branchfork 于某 seq · 共享祖先 revertTo快照回退 · 事件追加

重开 / daemon 重启：recover() 补到一致点（上次被 kill -9 遗留的悬空工具调用补 interruptedResult，不删事件）；编排运行由 resumeTasks() 接着跑。

一次 session.submit 的时序

daemon→DomiSession
checkCredential → checkInputs → busy=true → deliverNotices → loadMode（从事件流恢复确认模式）→ loadPlan → ensureTrust → freeze（turn 开始定格 soul/rules/catalog）→ preflight（上下文硬顶预检）
DomiSession→事件流
ctx.ref? / ctx.fileref? + user.input
kernel→事件流
循环① deliverNotes（运行中补充，安全点）→ buildContext（事件投影成 messages）

kernel→事件流

ToolRunner.run → 默认拒绝 / 配置放行 / 问人（见 §05 权限链路）

03 · 任务编排（DAG）

状态是事件的投影，循环是无状态的 drive

DAG 用 YAML 定义，运行不落任何状态文件——每步之前重读事件流，从投影里挑下一个节点。这就是「杀不死」：kill -9 之后重放事件即回到原处。

四种节点

agent-step · prompt + model tool · tool + args sub-agent · goal + tools human-approval · message

spec 用 zod 校验（id 唯一 / needs 存在 / 无环）；拓扑序（Kahn）在加载期算好并做环检测，跑错了在 start 时就报，不在运行期猜。

run- 会话的约定

任务 = 一个 run-… 会话，只编排不调模型；顶层任务动手前必须由模型用 plan.update 写计划（AC-8）；sub-agent 派生受 MAX_SPAWN_DEPTH 限制，子会话事件与父隔离。

TaskService 的一次驱动

调用方→TaskService
task.start(spec YAML) → validateSpec（拓扑序 + 环检测）→ 建 run- 会话 → 落 task.run（spec 快照）
runner→事件流
重读事件 → runState（纯投影）→ nextNode =「needs 全部 done 的第一个 pending」（拓扑序）
runner→事件流
task.node { status:"started" }
runner→执行器
agent-step = 子会话提交 prompt · tool = 直接调工具 · sub-agent = task.spawn 派生会话后取 lastAnswer · human-approval = askApproval（没人回答 = 否）
执行器→事件流
task.node { status:"done|failed", ms, output≤4000, error≤2000, sessionId? }
runner→循环
nextNode = null → task.end { status:"done|failed|cancelled" } → 系统通知（失败列节点名）

中断 / 恢复的三种路径（都不删事件）

重放kill -9 后重开：事件流原样，runState 投影回最后一致点
task.resume落 { completed, rerun }：中断时 running 的节点回 pending 重跑，继续 drive
task.retry只把失败节点重置为 pending、下游标 blocked（downstreamOf），重新 drive
04 · 权限链路

默认拒绝，每一次放行都是一条事件

权限引擎在 capability 包，模式经事件 permissions.mode.switch 持久化——重开会话照样生效。决策来源五个：default / config / user / mode / session-grant。

一次工具调用：判定 → 询问 → 放行

kernel→权限引擎
tool.call → ToolRunner.run → PermissionEngine.check（模式 + config 规则 + 本会话 grant）
引擎→事件流
permission { capabilityId, decision: allow|deny|ask, source, matchedRule? }
引擎→daemon
decision=ask → 推 session.ask（capabilityId + 完整 detail + form schema? + grantable?）
daemon⇄任一客户端
session.ask 通知 → session.answer { allowed, content?, channel?, grant? }；被另一端答掉后其余端收到 askDone 关弹窗
引擎→事件流
permission { decision, source:"user"|"session-grant", grant? } —— 落在 tool.result 之前
工具→kernel
执行 → tool.result { ok, payload, ms, reason? }；拒绝时 reason = user_denied / permission_denied

没有客户端在线：任务停在询问上等，不替用户答；长任务会发系统通知「在等什么能力确认」（不含参数内容）。grant =「本会话始终允许」——恢复时从 permission{source:"user", grant} 事件重放（recover 的 restoreGrants）。

05 · 定位与边界

它是谁，它拒绝成为谁

成功标准里写得很直白：项目的真实目标是个人实践与能力证明，不是社区影响力——把标准从“有多少人用”换成“我能不能讲清楚它为什么这么设计”。

主用户是有 CLI 习惯的开发者，愿意为可控性接受配置成本，对“黑盒 agent”有戒心。明确不服务：非技术用户、要开箱即用零配置的人、要多租户/团队协作的组织。

反指标

出现即跑偏

v1 范围外，写死的不做

  • 多租户、账号体系、计费
  • 云端会话存储
  • 可视化流程编辑器
  • 协商式多 agent（辩论/投票）——只做上下文隔离的 sub-agent
  • 模型微调、自研模型
  • 原生移动端——Telegram 聊天桥接已整块移除（v1.3，ADR-030）

工程原则：引用优先

  • 可直接引用的真库，一律不自写——适配层薄到“删掉库换一个”只改一个文件
  • 只抄算法做精简版——读源码理解后自实现，取舍记录注明出处
  • 必须自己写——事件流内核、轨迹面板、压缩与记忆、Soul、评估体系
06 · 不变量

12 条不变量：违反任何一条 = 跑偏

不变量是全局唯一的“不准违反”清单，非重大决策不得修改。价值在于它少——12 条能在每次 review 时逐条对照；100 条等于 0 条。v1.1 把原 INV-02 与 INV-04（同属依赖边界）合并，v1.2 把「前缀只增不改」并进 INV-12，活跃条数始终 ≤ 12。

可自动化 → 机器守 编译期 / 提示词层 里程碑收尾人工对照（10 分钟） 守卫层级：物理隔离 > CI 规则 > 人工自觉
INV-01
会话是 append-only 事件流；事件类型只增不改，任意历史事件永远可解析
protocol 类型快照测试（CI）
事件只追加、不修改、不删除；事件类型永远只增不改。这是“轨迹可回放”与“评估以回放为唯一数据源”的物理前提。
INV-02

dependency-cruiser + 依赖白名单（CI）
kernel 不 import apps/*、不 import 具体存储/网络/模型 SDK 实现；三端（TUI / Web / 终端）只是视图层。原 INV-04 已并入本条。
INV-03
权限默认拒绝；每个权限决策产生一条可审计事件
单测默认值断言（CI）
没有显式授权就是拒绝；任何允许/拒绝都是一条事件，能在轨迹里看到。这也让权限本身成为可回放的证据。

INV-12

INV-13
评估以事件流回放为唯一数据源，不新增埋点；确定性回放层（L1）不得调用真实模型
删除 packages/eval 后 kernel/store 测试仍全绿；L1 无网络通过（CI）
轨迹与评估是一体两面：真实会话回放当 fixture，不额外埋点、不依赖真实模型，评估才可复现、可审计。

四个角色不是项目阶段，是每个里程碑内部的四个环节

domi 是探索性项目，一次性走完四角色 = 一次瀑布，PRD 必然在 M2 就作废。所以每轮都是 PM → 架构 → 工程 → QA → 复盘；而把“跑偏”焊死的，是下面这条回写门。

ROLE 01

产品专家 · PM

docs/prd/M{n}.md
门禁：每条 AC 可执行？有“不做什么”？
ROLE 02

资深架构师 · ARCH

docs/spec/M{n}.md
门禁：PRD 覆盖表完整？取舍有反悔条件？触及的 INV 都有 CI 守卫？
ROLE 03

资深工程师 · ENG

docs/tasks/M{n}.md + 代码
门禁：每个 TASK 有 prd 引用？失败测试先提交？main 一直绿？
ROLE 04

测试工程师 · QA

docs/qa/M{n}.md
门禁：每条 AC 有结论？INV 逐条审计？目标：证伪，不是确认。
回写门任何下游角色发现上游文档有问题 → 必须停下，回到上游改文档，再重新往下走。 commit 前缀 docs(writeback): 留痕。 回写次数是流程健康度指标——某里程碑零回写，大概率是下游在偷偷绕过，不是上游写得完美。

五个缺口与补丁：这套流程为什么不是普通瀑布

01瀑布 vs 探索性项目
补丁：四角色是每个里程碑内部的四个环节；PRD 分册（docs/prd/M{n}.md），每册在上一个里程碑 QA 结束后才写，吸收上一轮学到的东西。
02没有回写门（最重要的一条）
原流程单向，下游发现问题会“就地修正”——看起来负责，实际上一个月后 PRD 和代码各说各话，防跑偏的基准就没了。补丁：回写门 + docs(writeback): 前缀；严禁“心里知道文档错了，代码按正确的写”。
03“跑偏”没有定义，于是无法判定
补丁：PRD 分两层——不变量（全局 ≤ 12 条，违反 = 跑偏）+ 可协商项（改动只需回写，不算跑偏）。不变量的价值在于它少。
04四个角色全是生产者，没有判官——而判官不能是 AI
自己审自己必然放水，而且放水方式是“给出一个听起来很合理的理由”，这比直接违规更危险。补丁：判官是机器（能自动化的不变量必须自动化，CI 强制），人是终审；QA 必须开独立会话，只喂 PRD + 代码，不喂实现过程的对话历史。
05AI 上下文丢失导致的“合理偏离”
长任务里会话会断、上下文会被压缩，第三天的 AI 可能写出一段“看起来完全合理”但违反 INV-02 的代码。补丁：所有决策落盘成机器可读的约束（类型 / CI 规则 / 物理隔离），不只存在于对话或散文里；新会话强制加载三件套（见 §07）。

可追溯链

这条链断在哪里，腐蚀就从哪里进来。每里程碑收尾做一次 10 分钟对账，拉表看有没有空格。

INV-xx→ PRD-M{n}→ SPEC-M{n}→ TASK-M{n}→ TEST→ QA-AC ← 回写门 ── 上游文档
10 · 机器守卫

能自动化的不变量必须自动化——“靠 review 守住”等于没守住

三道防线的优先级：物理隔离 > CI 规则 > 人工自觉。下面这条阶梯解释了为什么决策必须变成机器能检查的形态。

LEVEL 1 · 物理隔离

根本写不出来

依赖白名单 + package.json 边界：kernel 想 import 存储实现，依赖配置层面就不允许，连犯错的机会都没有。

LEVEL 2 · CI 规则

写错了就红

类型快照、dependency-cruiser、任务 lint、出站域名白名单、回放断言——提交期强制，人想绕过得先跟 CI 打架。

LEVEL 3 · 人工自觉

靠收尾对照

其余不变量在里程碑收尾时人工逐条对照（10 分钟）。人工层只兜底，不承担主要防线。

决策形态的可靠性阶梯

同一个决策，写在不同的地方，可靠程度完全不同。

只在对话里说过
会丢（几乎必然）
写在 markdown 散文里
会被忽略（下游不一定读到）
写成 ADR 条目
人能查到，但不强制
写成类型定义
编译期强制
写成 CI 规则
提交期强制
写成物理依赖隔离
根本写不出来
每做一个架构决策，都要问一句：“这条怎么变成机器能检查的？” 变不成的，才退回写 ADR。

开工必读三件套 + 中断恢复五步

不加载这三份就开始写代码，是“合理偏离”最主要的发生场景——这也是 AGENTS.md 被焊进仓库的原因。
